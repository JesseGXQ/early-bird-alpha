# 组合实验 Runner 性能瓶颈分析

## 背景

`DiagnosticPortfolioExperimentRunner.run()`（`factors/diagnostic_portfolio/experiment.py`）是组合实验层的核心入口。此前有一轮分析给出的结论是：**主要耗时在于「非调仓时点」仍然过一遍权重机的开销**——即主循环对每个时间戳（无论是否调仓）都调用 `machine.update()`，非调仓日的调用是浪费。

本文用实测数据检验该结论，并给出真正热点与优化方向的排序。

## 实测方法

### 数据与环境

- 合成 ragged long panel：T = 7600 个交易日（1996-01 起）、P = 50 个品种、369,285 行。规模与 `weights.py` 设计注释中声明的真实规模（"默认约 7600 期 × 约 100 个品种"）同量级。
- 品种上市时间在前 400 个交易日内随机错开（真实还原 ragged 结构）；2% 样本置为 `eligible=False`。
- 覆盖三种 V1 配方 × 不同调仓间隔：

| 配置 | 配方 | 调仓间隔 |
| --- | --- | --- |
| mrls_int1 | `market_rank_ls` | 1（每日调仓） |
| mrls_int20 | `market_rank_ls` | 20 |
| mrls_int9999 | `market_rank_ls` | 9999（几乎不调仓，anchor 后移） |
| tiv1_int20 | `ts_inv_vol_gross_one` | 20 |
| tivtv_int20 | `ts_inv_vol_target_vol` | 20 |

### 计量手段

- 阶段分解：对 `align_inputs` / `build_panel_arrays` / `machine.update`（按调仓、非调仓分别累计）/ `build_weights_series` / `_compute_accounting_artifacts` 及其内部各 `compute_*` / `DecisionLedger.warnings|metadata` / `_build_result` 挂 `perf_counter` 探针。
- 热点定位：对无探针的干净 run 做 cProfile，按 cumulative 排序。

基准脚本为临时产物，未入库；本文所有数字均可在同等规模合成数据上复现。

## 核心结论：该说法不成立

「非调仓时点过一遍权重机」确实存在，但实测开销**只占总耗时 2% ~ 4%**。非调仓路径单次调用仅 **2.8µs**（`np.where(eligible, w, 0)` + 一次 copy + 一个 frozen dataclass），这已经是 Python 函数调用的地板价——把它优化到零，总耗时几乎不变。

各配置完整分解（总耗时与各阶段耗时，括号内为占比）：

| 阶段 | mrls_int20 | mrls_int1 | tiv1_int20 | tivtv_int20 |
| --- | --- | --- | --- | --- |
| **总耗时** | **0.52s** | **0.83s** | **0.55s** | **0.92s** |
| 会计阶段 `_compute_accounting_artifacts` | 0.318s (61%) | 0.322s (39%) | 0.317s (57%) | 0.320s (35%) |
| 权重机·调仓日 update | 0.018s (3.5%) | 0.332s (40%) | 0.043s (8%) | 0.333s (36%) |
| **权重机·非调仓日 update** | **0.020s (3.9%)** | — | **0.023s (4.1%)** | **0.024s (2.6%)** |
| `build_panel_arrays` 展开 | 0.079s (15%) | 0.078s (9%) | 0.084s (15%) | 0.081s (9%) |
| 主循环骨架（iat/切片/记账） | 0.046s (9%) | 0.059s (7%) | 0.048s (9%) | 0.049s (5%) |
| `DecisionLedger.metadata` | ~0s | ~0s | ~0s | 0.074s (8%) |

对该错误结论的来源推测：如果只对比"每日调仓 vs 每 20 日调仓"的总耗时（0.83s vs 0.52s），或只 profile 了 `interval=1` 的配置（此时 update 占 40%），容易得出"逐期 update 是瓶颈"的印象——但那是**调仓日**的真实计算成本，不是非调仓开销。mrls_int9999（仅 1 个调仓日）配置下总耗时仍有 0.50s，说明大头是与调仓频率无关的固定成本。

## 真正的热点

### 瓶颈 1：会计阶段 pandas groupby（约 0.32s，固定成本，常规配置下占 57% ~ 61%）

这是**与调仓频率无关**的最大项，各配置下稳定在 0.32s 左右。内部细分：

| 子项 | 耗时 | 主要操作 |
| --- | --- | --- |
| `_align_weight_return_cost` | 0.087s | `from_product` 造 7600×50 全笛卡尔网格 reindex + `groupby(level='product').shift(1)` + reindex 回 panel.index |
| `compute_attribution_product` | 0.076s | 约 5 次 `groupby(level=...)` |
| `compute_weight_changes_turnover_cost` | 0.055s | `groupby.diff` + `groupby.sum` |
| `compute_exposure` | 0.050s | 5 次 `groupby.sum` |
| `compute_attribution_direction` | 0.024s | 2 次 `groupby.sum` + reindex |

cProfile 证据：单次 run 中 pandas 的 `factorize`（groupby 每次 `groupby(level=...)` 都要重新对索引 codes 做 factorize）累计约 **0.11s**——也就是说约三分之一的会计时间花在"反复把同一组 MultiIndex 拆成 group codes"上，而非真正的统计计算。

结构性问题在于：`run()` 主循环已经刻意 numpy 化（`build_panel_arrays` / `build_weights_series` 的注释都写明了性能动机），但拿到 `weights_matrix` 后立刻 `build_weights_series` 展开回 MultiIndex Series，交给全是 pandas groupby 的会计函数——**前面省下的索引开销在会计阶段又全数还了回去**。而这些统计量本质上全是 `(T, P)` 矩阵上的逐行 numpy 运算：

- 贡献：$\Delta W$ 与 $R$ 错一行逐元素相乘，`weights_matrix[:-1] * true_return_matrix[1:]`
- 换手：$|\Delta W|$ 按行求和
- 暴露：$|W|$、$W$、$\max(W,0)$、$\min(W,0)$ 各按行求和
- 方向归因：按权重符号掩码的逐行求和

理论上可从 0.32s 降到 10ms 量级。

### 瓶颈 2：`ts_inv_vol_target_vol` 的协方差估计（0.333s，占该配方 36%）

`_scale_to_target_vol` → `ex_ante_portfolio_volatility_annualized` → `_covariance_matrix_pairwise`：每个调仓日约 0.9ms，380 个调仓日共 0.333s。成本构成：`DataFrame.cov()`（pairwise complete 口径）+ `np.linalg.eigh` PSD 修复。

`risk.py` 注释已说明保留 `df.cov()` 的精度理由（充分统计量向量化在收益量级 ~1e-2 下会因相消损失数位有效数字），属于有意取舍，不是无脑浪费。但两点值得注意：

- 只发生在调仓日，与"非调仓开销"无关；
- 复杂度按 $O(P^3)$ 放大：P=50 时 0.33s，真实品种数 ~100 时预计升至 2s 以上，届时会成为该配方的第一瓶颈。

### 瓶颈 3：`DecisionLedger.metadata`（仅 target_vol 配方，0.074s，占 8%）

380 个 6 行的 meta Series 逐个 `m.rename(timestamp).to_frame().T` 再 `pd.concat`。逐条构造 DataFrame 的对象开销远大于数据本身。

### 瓶颈 4（小项）：主循环骨架 0.046s ~ 0.059s

其中相当一部分是 `rebalance_flags.iat[i]`——循环内逐次走 pandas 标量引擎取一个 bool。循环前先 `rebalance_flags.to_numpy()` 即可消除。绝对收益小（~0.02s），属于顺手改。

`build_panel_arrays`（0.08s，3 次 unstack + reindex）是一次性准备成本，规模合理，暂无必要动。

## 顺带发现的潜在 bug：全零权重时 `_collect_date_range_metadata` 崩溃

`experiment.py` `_collect_date_range_metadata` 中：

```python
_w = target_weights.where(target_weights != 0)
first_nonzero_gross_expsoure_ts = _w.first_valid_index()[0]
```

当整段实验从未形成有效组合（`_w` 全为 NaN）时，`first_valid_index()` 返回 `None`，`None[0]` 抛 `TypeError`——而 docstring 承诺"找不到则为 None"。触发条件实测可复现：首个（且唯一）调仓日有效品种数 < `min_cross_section_size`、之后不再调仓（如 `interval=9999`）。`last_valid_index()` 同理。

这是与性能无关的正确性问题，但任何"把调仓间隔拉大做稳健性检查"的实验都可能踩到。

## 优化方向建议（按收益排序）

1. **会计阶段矩阵化**（预期 -0.3s，全部配方普适，优先级最高）
   让 `_compute_accounting_artifacts` 直接消费主循环已持有的 `weights_matrix` / `true_return` 矩阵，按行做 numpy 运算，仅在最终输出边界构造一次 MultiIndex。需要重构 `accounting.py` 各 `compute_*` 的输入接口（或在 experiment 层新增矩阵版实现、保留 Series 版给测试/外部调用）。注意保持口径不变：决策时点 t 的权重对应收益实现时点 t+1、第一期剔除、`missing_return_policy` 的 NaN 处理。
2. **`ts_inv_vol_target_vol` 协方差估计降本**（预期 -0.2 ~ -0.3s，仅该配方；P=100 时收益更大）
   方向包括：调仓间隔内协方差窗口不变时复用上次结果（窗口每次前移 interval 期，通常无法直接复用，需评估）；`df.cov` 与 `eigh` 的分解与增量更新；或在数值精度允许处改用充分统计量并配合中心化预处理避免相消。此项与精度取舍耦合紧，建议在矩阵化之后再做，并配数值对拍测试。
3. **`DecisionLedger.metadata` 改单次构造**（-0.07s，改动小）
   收集期为 dict 列表，最后一次 `pd.DataFrame.from_records`；或仅在 `cov_mat_estimation_meta` 非 None 时登记。
4. **`rebalance_flags` 循环前转 numpy**（-0.02s，一行改动）
5. **修全零权重崩溃**（正确性修复，改动小）：`first_valid_index()` 为 None 时显式记 None。
6. **不建议做**：优化非调仓 update 路径。2.8µs/次已是函数调用地板价，收益上限 0.02s，不值得为它增加状态机分支复杂度。

## 有效性说明

- 数据为合成数据，分布与真实收益不同，但各阶段的操作类型、行数、调用次数与真实场景一致，占比结论稳健；
- P=50 下的占比在 P=100 时会有偏移：groupby 类成本约按行数线性放大，协方差估计按 $O(P^3)$ 放大（见瓶颈 2）；
- 单机单次运行数字有 ±10% 左右波动，本文取的是多次观察的典型值。
