# 数据分发方案：git 提交与 Releases 混合

## 面临的问题

仓库当前只入库代码与规则 YAML，行情、派生表等 parquet/csv 数据全部被 `.gitignore` 排除，用户 clone 后拿不到可运行的数据。计划公开仓库并一并提供数据（当前工作区待入库约 117.6MB、494 个文件，最大单文件 16.8MB，更新频率低），需要同时满足两个目标：用户 clone 即可获得最新代码与数据；仓库体积不随数据更新失控。矛盾点在于 parquet 是压缩二进制，git 的增量压缩对其几乎无效，每次全量重写都近似新增一份全量对象——按月更新一年后仓库约 1.5GB，两年约 2.9GB，每个新用户都要为全部历史付费。LFS 不适合本场景（配额按账号共享、按月计费，公开仓库被多次 clone 即耗尽且用户需额外安装 git-lfs），网盘则存在限速、需登录、链接失效、与代码版本无法对应等问题。

## 阶段一：直接提交进 git（当前采用）

把清洗后与派生的数据（约 100MB）直接 `git commit` 进仓库，不使用 LFS。README 首推轻量用法 `git clone --depth 1 <url>`，只取最新快照、不背历史，并注明需要完整历史时用 `git fetch --unshallow`。配套三条约定：数据文件尽量只增不改，按品种、按年分片，避免反复覆盖单个大文件（`upper_lower_price_limits` 那类单一 16.8MB 文件最应拆分）；`db/` 下的数据仅由维护者提交，PR 只收代码，避免二进制冲突无解；入库前完成历史凭证扫描，并确认第三方数据源的再分发条款。

## 阶段二：迁移到 manifest + Releases 混合方案

当数据超过 500MB，或开始每月全量重写导致历史以每月 100MB 以上膨胀时迁移。做法是：仓库内只保留一份 `data_manifest.json`（记录 release tag、每个文件的 sha256 与大小），数据本体作为 GitHub Releases 的 assets 分发；发布侧脚本扫描 `db/` 计算哈希、提交 manifest、用 `gh release create/upload` 上传变更文件；拉取侧脚本读取当前 commit 的 manifest，逐个比对 sha256，只下载缺失或不匹配的文件并校验。这样历史里不再有二进制，clone 体积恒定，同时通过 manifest 把数据版本精确绑定到代码 commit，可复现性、完整性校验、按文件增量更新三者兼得；代价是数据不再 clone 即有，用户需多跑一条 fetch 命令，且 GitHub 下载在国内可能不稳定，必要时可另设国内镜像。

## 迁移成本

方案可平滑演进：phase 1 保持 `db/` 归数据、其余目录归代码的边界，迁移时即为纯机械操作——把 `db/` 移出仓库、生成 manifest、上传 assets，用户侧只需新增一条 fetch 命令，不会产生破坏性变更。因此现阶段无需提前实现，只需守住目录边界与分片约定。
