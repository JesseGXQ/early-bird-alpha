# 数据引擎桥接层设计

## 1. 思路与边界

因子研究早期，数据需求高度探索性，不宜每试一个因子就扩展数据引擎和 `ResearchDatasetBuilder`。
因此在因子模块内建立一个薄的**桥接层**：根据因子声明的 `DataRequirement`，通过 `DataFacade` 或本地数据组件取数，直接产出因子 `compute()` 所需的数据结构。

边界：

- 引擎负责 canonical data 及其语义（换月、复权、主连、交易日历等）；桥接层只负责“取数 + 简单校验”。
- 不复制引擎语义。优先调用 `DataFacade` / 现有 manager / loader；确需读本地库时复用已有组件，不另写清洗逻辑。
- 不做因子专用的 join、对齐、ffill、标准化；这些留在因子内部。
- 仅研究层使用，不向 `backtester` / `executor` 等生产路径提供依赖。
- 桥接层可暂时绕过 `ResearchDataset.auxiliary`，为研究期临时安排，不是稳定契约。

### 可复现性

当前不引入额外的 manifest 或数据指纹。`diagnostic_portfolio/storage` 已记录 `DatasetSpec.data_requirements`，桥接数据也通过因子的 `DataRequirement` 声明，因此可追溯“因子需要哪些数据、哪些列”即可。现阶段不以可复现性为设计重心。

## 2. 明确缺口的分层处理

| 层级 | 情况 | 处理 |
|---|---|---|
| T1 | 字段已在引擎原始数据中，只是未暴露 | 直接补引擎（例如 `RFEED_1d_COLUMNS` 增加涨跌停两列） |
| T2 | 数据在本地库，但引擎无接口 | 桥接层 adapter，复用现有 manager / loader；稳定后再上移 |
| T3 | 派生、昂贵或外部数据 | 桥接层负责取数与派生；不进 `ResearchDataset` |
| T4 | 因子特有的 join、对齐、变换 | 留在因子内部 |

即：能一行暴露的字段就走引擎；需要新数据产品或派生视图的，先走桥接层。待同一数据源被多个因子重复使用、语义稳定、或生产层也需要时，再“提升”到引擎；迁移时保持 source 名不变，无需改因子代码。

## 3. 桥接层形态

位置：`factors/bridge.py`（单文件）。

```python
class FactorDataBridge:
    def __init__(self, facade: DataFacade, dataset: ResearchDataset | None = None): ...

    def resolve(
        self,
        requirements: tuple[DataRequirement, ...],
        *,
        products: list[str],
        start_date: date,
        end_date: date,
    ) -> pd.DataFrame | dict[str, pd.DataFrame]: ...
```

约定：

- 只提供 `resolve`，不提供 `compute`，不承担实验编排。
- 单个 `DataRequirement` 返回 `DataFrame`；多个返回 `dict[source, DataFrame]`。因子 `compute` 的入参形式在 docstring 中写明。
- 按需加载，只取 `requirements` 声明的数据源与列。
- 若传入 `ResearchDataset`，`main_panel` / `term_structure` / `warehouse_receipt` 优先复用 dataset 中的数据；缺失时再通过 facade 补取。
- V1 不做缓存，每次按 `DataRequirement` 重新取数、重新计算。
- 不做 warm-up 扩展；日期范围由调用方显式给出。
- 数据源通过内部注册表映射到 loader；新增探索性数据源只需增加一个 loader。
- 对每个 source 做轻量 schema 校验（索引名、必需列、是否允许为空），错误显式抛出或记录 warning，不静默返回错误数据。
