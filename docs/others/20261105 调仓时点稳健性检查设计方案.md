## 设计摘要

- **位置**：`factors/diagnostic_portfolio/rebalance_timing.py`，不新建顶层 `factors/robustness/`。
- **形式**：frozen dataclass 配置/结果 + 纯函数 + 一个薄编排函数；不新增有状态 class。
- **核心输出**：每个 `h` 的相位分布（`count/mean/std/min/median/max`）与 `anchor=0` 分位。
- **评价口径**：默认共同评价窗口；同时保留 per-anchor 口径用于对照。
- **边界**：只做 anchor 相位诊断，不替代 walk-forward / 样本外检验；不与 Overlapping Tranches 混为一谈。

## 一、背景与问题

CurveSlope 单因子实验使用单一调仓锚点（`anchor=None`，即时间轴起点）扫描持有期 `h`。在 `h=55` 处，代理净 Sharpe 达到 1.171，明显高于相邻持有期。

把同一 `h` 的调仓起点换成 20 个不同相位后，结果变成：

- `h=55`、`anchor=0` 的 Sharpe 为 1.171；
- 20 个相位的均值为 0.946，标准差为 0.131；
- `anchor=0` 是 20 个相位中的最高值，约高于相位均值 1.7 个标准差；
- 相邻持有期的相位均值与 `h=55` 接近：`h=50` 为 0.925，`h=51` 为 0.934，`h=54` 为 0.913，`h=56` 为 0.918，`h=59` 为 0.952。

这说明 `h=55` 的尖峰主要来自**调仓时点相位选择**，而不是稳健的 55 天持有期最优。单一 anchor 的持有期扫描很容易把“某个相位恰好避开了坏区间/撞上了好区间”误读成参数优势。

这类问题在文献中通常称为 **rebalance timing luck** 或 **rebalance schedule sensitivity**。它属于组合实现层的稳健性问题，不是因子的预测内容问题。

因此需要一个可复用的诊断组件：把“固定因子、固定组合规则、只改变调仓相位”的检查从一次性 notebook 代码变成研究基础设施。

## 二、目标与非目标

### 2.1 目标

该组件要回答的问题是：

> 某个持有期 `h` 的最优表现，是来自参数本身，还是来自某一个调仓相位？

具体能力：

- 固定因子、数据集、组合 spec，只改变 `RebalanceConfig.anchor`；
- 对每个 `h` 生成一组确定性的 anchor 相位；
- 复用现有 `DiagnosticPortfolioExperimentRunner` 运行每个相位；
- 输出每个相位的绩效，以及每个 `h` 的相位分布；
- 标出原始 `anchor=0` 结果在自身相位分布中的位置；
- 结果可复现、可审计、可单元测试；
- 不重算因子，不复制组合记账逻辑。

### 2.2 非目标

- 不建设统一稳健性框架、优化器、中央实验注册服务或报告平台；
- 不替代 walk-forward、最终留出样本或多重检验校正；
- 不实现 placebo 信号、block bootstrap、区间分解等扩展诊断；这些可以作为后续独立工具；
- 不修改 `DiagnosticPortfolioExperimentRunner` 的公共接口；
- 不自动选择 `h`，也不给出“通过/不通过”阈值或稳健性总分；
- 不与 Overlapping Tranches 混为一谈：后者是组合构造层面的缓释方案，本组件是诊断工具。

## 三、概念与术语

| 术语 | 含义 |
|---|---|
| anchor | `RebalanceConfig.anchor`，调仓日程的起始时点；`None` 等价于时间轴第一个时点 |
| anchor offset | anchor 在权威交易日时间轴上的位置偏移（交易日索引，不是自然日） |
| phase / 相位 | 由 anchor 决定的调仓时点集合；不同 offset 对应不同相位 |
| anchor=0 | 现有单 anchor 扫描使用的相位，即 `anchor=None` |
| phase distribution | 同一 `h` 下，不同 anchor 相位的绩效分布 |
| anchor0 percentile | `anchor=0` 在自身相位分布中的分位 |
| rebalance timing luck | 单相位结果因调仓日期与少数收益区间重合而偏好的现象 |

**anchor 稳健性检查**只回答“结果对调仓相位有多敏感”，不回答“这个因子是否有效”。因子有效性的证据仍来自预测统计量、经济解释、样本外检验和多重检验。

## 四、职责边界

### 4.1 组件负责

- 根据 `spec.rebalance.interval` 与时间轴生成 anchor offsets；
- 构造 anchor 变体（每个变体是一个新的 `DiagnosticPortfolioSpec`）；
- 调用现有 Runner 运行每个变体；
- 从 `DiagnosticPortfolioResult` 提取绩效、换手、暴露等指标；
- 汇总相位分布，计算 anchor0 分位；
- 记录评价窗口、anchor 列表、指标口径与警告；
- 在相位样本不足、Sharpe 未定义等边界情况下保留行并标记状态。

### 4.2 调用方负责

- 准备因子值、数据集和基础 `DiagnosticPortfolioSpec`；
- 选择要检查的 `h` 集合（组件一次只处理一个 `h`，多 `h` 由调用方循环）；
- 决定 anchor 的采样方式（全部相位、均匀采样或显式列表）；
- 解释结果，不把相位分布当作 p 值或显著性检验；
- 决定是否进一步做 walk-forward、placebo、block bootstrap 等扩展分析。

### 4.3 组件不负责

- 不加载数据、不计算因子、不做预处理；
- 不重新实现权重、收益、成本或绩效公式；
- 不修改 `DiagnosticPortfolioResult` 的字段；
- 不做自动参数搜索；
- 不持久化完整相位家族（V1 由调用方保存 `runs` / `summary`）。

## 五、架构位置

### 5.1 结论

新增：

```text
factors/diagnostic_portfolio/rebalance_timing.py
```

并从 `factors/diagnostic_portfolio/__init__.py` 导出公共接口。不修改 `factors/__init__.py` 的框架级导出。

### 5.2 为什么不放顶层 `factors/robustness/`

1. **语义归属**：调仓时点运气是组合实现层属性，不是因子预测属性。它的输入天然是 `DiagnosticSignal`、`ResearchDataset`、`DiagnosticPortfolioSpec` 和 Runner。
2. **依赖方向**：该组件必须调用组合引擎。如果放进通用的 `factors/robustness.py`，会形成“通用稳健性工具 → 组合引擎”的反向依赖。
3. **设计文档边界**：[因子研究的稳健性检验开发方案](<../Development Notes/20261022 因子研究的稳健性检验开发方案.md>) 明确把 `factors/robustness.py` 定位为时间切分、walk-forward、参数邻域等研究层工具，并写明统计模块“不调用组合引擎”。
4. **避免框架膨胀**：顶层 `factors/robustness/` 容易变成一个什么都往里放的包，最终长成设计文档首期明确不建设的“统一稳健性运行器”。
5. **命名冲突**：设计文档预留的是 `factors/robustness.py`（单模块），不是 `factors/robustness/`（包）。现在建包要么冲突，要么需要改设计文档。

### 5.3 与其他模块的关系

- `factors/evaluation/robustness.py`：继续放 p 值校正、HAC 均值检验等统计工具；不导入组合引擎。
- `factors/robustness.py`：继续放时间切分、标签成熟度、参数邻域等研究层工具；不导入组合引擎。
- `factors/diagnostic_portfolio/`：本组件与 Runner、Spec、会计模块同层，依赖关系最自然。

### 5.4 什么时候升级为子包

当组合层稳健性检查积累到 3 个以上时，再考虑：

```text
factors/diagnostic_portfolio/robustness/
    __init__.py
    models.py          # 共用 config/result
    timing.py
    cost.py
    universe.py
    constraint.py
```

典型触发条件：

- rebalance timing / anchor sensitivity；
- cost sensitivity；
- universe / eligibility sensitivity；
- constraint sensitivity；
- signal lag sensitivity。

在只有 anchor 检查一个需求时，不提前建子包。

## 六、接口设计

### 6.1 总体风格

采用：

- **frozen dataclass** 表达配置与结果；
- **纯函数**处理 anchor 生成与汇总；
- **一个薄编排函数**负责实际运行；
- **不新增有状态的 class**。

理由：

- `DiagnosticPortfolioExperimentRunner` 已经是 class，再包一层 class 会形成两层状态，测试和组合都更麻烦；
- 纯函数容易用合成数据测试；
- 薄编排函数可以注入 runner factory，避免单元测试依赖真实数据；
- 与现有 `run_scan`、`precompute_shared_factors` 的函数式风格一致。

### 6.2 配置

```python
@dataclass(frozen=True)
class AnchorRobustnessConfig:
    n_anchors: int | None = 20
    offsets: tuple[int, ...] | None = None
    metrics: tuple[str, ...] = (
        'gross_sharpe',
        'proxy_net_sharpe',
        'proxy_net_cagr',
        'annualized_volatility',
        'max_drawdown',
        'avg_turnover',
        'avg_active_count',
        'n_rebalances',
    )
    quantiles: tuple[float, ...] = (0.1, 0.5, 0.9)
    percentile_method: Literal['weak', 'midrank'] = 'weak'
    evaluation_window: Literal['common', 'per_anchor'] = 'common'
    min_rebalances: int = 2
```

约束：

- `offsets` 与 `n_anchors` 二选一；同时给出时以 `offsets` 为准，或直接报错，避免隐式覆盖；
- `offsets` 必须是非负整数、唯一、严格小于 `interval`；
- `n_anchors` 必须是正整数，且不超过 `interval`；
- `quantiles` 必须在 `[0, 1]` 内且升序；
- `min_rebalances` 至少为 1，默认 2，保证至少能形成一次完整持有期比较；
- `metrics` 只接受预定义指标名（上方列表），不接受任意表达式或回调；新增指标时在组件内显式增加，避免变成通用指标引擎。

### 6.3 anchor 变体

```python
@dataclass(frozen=True)
class AnchorVariant:
    h: int
    anchor_offset: int
    anchor: pd.Timestamp
    spec: DiagnosticPortfolioSpec
```

`spec` 是通过 `dataclasses.replace` 从基础 spec 复制出来的新对象，不修改调用方传入的 spec。

### 6.4 结果

```python
@dataclass(frozen=True)
class AnchorRobustnessResult:
    runs: pd.DataFrame
    summary: pd.DataFrame
    config: AnchorRobustnessConfig
    warnings: tuple[str, ...]
    metadata: Mapping[str, Any]
```

`runs` 一行对应一个 anchor 相位，至少包含：

```text
h, anchor_offset, anchor, status,
gross_sharpe, proxy_net_sharpe, proxy_net_cagr,
annualized_volatility, max_drawdown,
avg_turnover, avg_active_count, n_rebalances,
warnings
```

`summary` 以 `h` 为索引，至少包含：

```text
count, mean, std, min, median, max, anchor0, anchor0_percentile
```

可选追加 `q10`、`q90` 等分位列；不追加“稳健性总分”。

`metadata` 至少记录：

- 信号名、因子名；
- 基础 `DiagnosticPortfolioSpec` 的关键字段；
- `h`、anchor offsets、anchor 日期列表；
- 评价窗口起点/终点；
- 指标定义与年化因子；
- Runner 版本或提交标识（若可得）。

### 6.5 纯函数

```python
def generate_anchor_offsets(
    interval: int,
    timeline: pd.DatetimeIndex,
    *,
    offsets: Sequence[int] | None = None,
    n_anchors: int | None = None,
) -> tuple[int, ...]: ...
```

约定：

- offset 是**交易日索引**，不是自然日；
- `anchor=None` 对应 offset 0；
- `n_anchors` 使用确定性的均匀取点，例如
  `np.unique(np.linspace(0, interval - 1, n_anchors).round().astype(int))`；
- 不默认随机采样；若未来支持随机采样，必须显式 seed 并记录；
- 校验 anchor 不晚于 `timeline[-2]`；
- 校验每个 anchor 至少能形成 `min_rebalances` 次调仓，否则保留并标记警告。

```python
def build_anchor_variants(
    spec: DiagnosticPortfolioSpec,
    timeline: pd.DatetimeIndex,
    *,
    offsets: Sequence[int] | None = None,
    n_anchors: int | None = None,
) -> tuple[AnchorVariant, ...]: ...
```

`h` 从 `spec.rebalance.interval` 读取，不单独传入，避免 spec 与 h 不一致。

```python
def summarize_anchor_runs(
    runs: pd.DataFrame,
    *,
    anchor0_offset: int = 0,
    quantiles: Sequence[float] = (0.1, 0.5, 0.9),
    percentile_method: Literal['weak', 'midrank'] = 'weak',
) -> pd.DataFrame: ...
```

分位定义：

- `weak`：`mean(x <= anchor0)`，与当前 notebook 表格一致；
- `midrank`：`(count(x < anchor0) + 0.5 * count(x == anchor0)) / n`，对并列更稳健。

默认保留 `weak` 以兼容 notebook 结果；正式研究建议在文档中明确所选方法，不根据结果临时切换。

### 6.6 薄编排函数

```python
def run_anchor_robustness(
    signal: DiagnosticSignal,
    dataset: ResearchDataset,
    spec: DiagnosticPortfolioSpec,
    config: AnchorRobustnessConfig,
    *,
    runner_factory: Callable[..., DiagnosticPortfolioExperimentRunner]
        = DiagnosticPortfolioExperimentRunner,
) -> AnchorRobustnessResult: ...
```

流程：

1. 从 `dataset.main_panel` 取得权威交易日时间轴（与现有 `build_global_timeline` 口径一致）。
2. 生成 anchor offsets 与 `AnchorVariant`。
3. 对每个变体调用 `runner_factory(signal=..., dataset=..., spec=variant.spec).run()`。
4. 从 `DiagnosticPortfolioResult` 提取指标。
5. 按评价窗口切齐，汇总 `runs` 与 `summary`。
6. 聚合警告与 metadata。

`runner_factory` 只用于测试注入，不改变生产路径。

## 七、评价口径

### 7.1 共同评价窗口

不同 anchor 的起点不同。如果直接比较 `proxy_net`，早期 anchor 可能比晚期 anchor 多出一段建仓前空仓期，导致口径不完全一致。

V1 建议：

- 默认 `evaluation_window='common'`；
- 以 `timeline[max(offsets) + interval]` 作为共同评价起点，给最晚启动的相位至少一个完整持有期；
- 评价终点统一为 `timeline[-1]`；
- 从 `result.portfolio_returns` 切片后，复用 `compute_performance` 计算同一套指标；
- 在 `metadata` 记录实际评价窗口和每行的 `n_periods`。

同时保留 `evaluation_window='per_anchor'`：

- 用于和当前 notebook 的 `proxy_net` 口径对照；
- 报告中必须明确它包含不同长度的启动期。

如果认为共同窗口太短，可以另加 `warmup_periods` 参数；V1 先用一个 `interval` 的 warmup，避免接口过早复杂化。

### 7.2 指标

至少输出：

| 指标 | 来源 |
|---|---|
| `gross_sharpe` | `performance.loc['gross', 'sharpe']` |
| `proxy_net_sharpe` | `performance.loc['proxy_net', 'sharpe']` |
| `proxy_net_cagr` | `performance.loc['proxy_net', 'cagr']` |
| `annualized_volatility` | `performance.loc['proxy_net', 'annualized_volatility']` |
| `max_drawdown` | `performance.loc['proxy_net', 'max_drawdown']` |
| `avg_turnover` | `result.turnover.mean()` |
| `avg_active_count` | `result.exposures['active_count'].mean()` |
| `n_rebalances` | `result.rebalance_flags.sum()` |

不要只返回 Sharpe。否则“成本下降”“换手下降”或“截面变宽”都可能被误读为信号变好。

### 7.3 分位与结论表述

相位分布是**敏感性分布**，不是显著性检验：

- 可以报告 phase mean/median/std、10%–90% 分位、anchor0 分位；
- 不把 anchor0 分位写成 p 值；
- 不说“anchor=0 显著优于其他相位”；
- 不设置“稳健性通过阈值”；
- 可以描述“anchor=0 位于相位分布上尾”“相位均值与邻居接近”，并据此判断参数选择是否依赖单相位。

## 九、运行流程与复杂度

### 9.1 流程

```text
准备 factor values / dataset / base spec
    → 对每个 h：
        → generate_anchor_offsets
        → build_anchor_variants
        → 逐个调用 Runner
        → 提取指标、切齐评价窗口
        → summarize_anchor_runs
    → 合并多 h 的 summary
```

因子只需计算一次，所有 anchor 复用同一份因子值。这是该组件相对“每次重算因子”的关键优势。

### 9.2 运行时间

组合 Runner 单次运行约为秒级；当前 CurveSlope 规模下，10 个 h × 20 个 anchor ≈ 200 次 Runner，约 2–3 分钟。主要成本仍是因子预计算，不在本组件。

V1 不引入并行化。若未来全 h（5–60）× 全部相位（最多 60）变得常用，再评估 `n_jobs` 或分批运行；不在首期引入新依赖。

### 9.3 内存

每次 Runner 的结果包含 `target_weights`、`portfolio_returns` 等中期对象。V1 不保留所有 phase 的完整权重历史，只保留：

- `runs` 的指标行；
- 可选的逐日收益（用于后续区间分解）；
- `summary`。

如果调用方需要完整结果，可逐个保存 `DiagnosticPortfolioResult`，或后续引入相位家族 manifest。

## 十、警告与边界

至少处理以下情况：

| 情况 | 行为 |
|---|---|
| anchor 太晚，剩余样本不足 `min_rebalances` | 保留行，`status='TOO_SHORT'`，警告 `ANCHOR_TOO_SHORT` |
| anchor 超出 `timeline[-2]` | 构造阶段直接报错 |
| Sharpe 未定义（样本不足、标准差为零） | 保留行，`status='SHARPE_UNDEFINED'` |
| 信号全相等 / 截面不足 | 沿用 Runner 的空仓与警告，不在组件内重复实现 |
| 缺失收益被零填充 | 聚合 Runner 警告，记录数量与品种数 |
| 全部 anchor 失败 | 返回结构稳定的空/全 NaN 结果，不静默成功 |
| 输入 timeline 非唯一、非升序、含 NaT | 直接报错 |
| `offsets` 重复、为负、超出 `interval` | 直接报错 |

组件不删除失败 anchor，也不为了让曲线好看而补零或插值。

## 十三、与 Overlapping Tranches 的关系

两者解决的是同一个问题的不同层面：

| 工具 | 角色 | 作用 |
|---|---|---|
| Anchor robustness check | 诊断 | 测量单相位结果对 anchor 的敏感度 |
| Overlapping Tranches | 缓释/构造 | 把研究预算分散到多个错开调仓的批次，降低单相位依赖 |

推荐顺序：

1. 先用 anchor robustness check 判断是否存在明显的 timing luck；
2. 如果存在，再评估 Overlapping Tranches 是否能降低相位分散度；
3. 两者都不能替代 walk-forward / 最终留出样本。

Overlapping 方案已经引用了当前 `h=55` 的 anchor 结果；本文档提供该检查的详细设计，二者不重复。

## 十五、待确认事项

以下问题在实施前需要明确：

1. **默认 anchor 数量**：20 个均匀相位，还是 `h` 个全部相位？全部相位更严谨，但全 h 扫描成本更高。
2. **主指标口径**：默认共同评价窗口，还是与当前 notebook 一致的 `proxy_net`？建议共同窗口为主、`per_anchor` 为辅。
3. **分位定义**：默认 `weak (<=)` 兼容 notebook，还是 `midrank` 更稳健？建议文档明确固定一种，不根据结果切换。
4. **编排边界**：组件是否直接调用 Runner，还是只提供 anchor 生成 + 汇总、由 notebook 调用 Runner？本文建议提供薄编排函数，但保留纯函数以便调用方自行编排。
5. **多 h 接口**：核心接口只处理单个 h，多 h 由调用方循环；是否需要 `run_anchor_robustness_grid` 便捷函数？
6. **存储**：V1 是否只导出 `runs` / `summary`，还是需要相位家族 manifest？建议 V1 不扩展 `DiagnosticPortfolioStore`。
7. **命名**：模块名用 `rebalance_timing.py` 还是更宽的 `robustness.py`？建议先用 `rebalance_timing.py`，等第二个组合层检查出现再改名/升级子包。
