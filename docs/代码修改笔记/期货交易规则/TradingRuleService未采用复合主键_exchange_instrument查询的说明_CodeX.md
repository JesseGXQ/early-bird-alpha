# Trading Rules 模块设计说明

## 查询键约定

当前 `data/rules` 模块面向中国境内期货市场，查询键暂不包含
`exchange`：

```text
品种查询键：product
合约查询键：instrument
合约日频状态查询键：(instrument, trading_date)
```

这一设计基于以下系统约束：

1. 在系统当前覆盖的市场范围内，`product`（品种代码）全局唯一，并且
   一个 `product` 只属于一个交易所。
2. `instrument`（合约代码）全局唯一，可以通过合约注册表唯一确定其
   `product` 和 `exchange`。
3. `exchange` 仍然是品种和合约的重要领域属性，由品种元数据或合约
   注册表提供，但调用方无需在每次内部查询时重复传入。

使用单字段查询键可以减少接口参数及矛盾输入。例如，若同时传入
`exchange="DCE"` 和 `instrument="RB2610"`，系统还需要额外判断应当
相信调用方提供的交易所，还是合约注册表中的交易所。

## 数据完整性要求

数据加载阶段应验证上述约束，至少包括：

- 每个 `product` 只能对应一个 `exchange`；
- 每个 `instrument` 只能对应一条合约注册记录；
- 合约注册表中的 `product` 和 `exchange` 必须与品种元数据一致；
- 文件名中的 `exchange`、`product` 必须与文件内容一致。

如果发现代码重复或映射冲突，应在加载阶段明确报错，不应静默选择其中
一条记录。

## `exchange` 的保留位置

不把 `exchange` 作为当前内部查询主键，不代表从领域模型中删除它。
以下位置仍应保留 `exchange`：

- 品种元数据和合约注册信息；
- 按交易所组织的数据文件及目录；
- 行情、交易柜台和其他外部数据的接入边界；
- 订单路由、报单及交易所规则处理；
- 数据导入和一致性校验。

## 未来需要重构的情形

如果出现以下任一情形，应重新评估并将查询键升级为复合键：

- 不同交易所出现相同的 `product` 代码；
- 不同交易所出现相同的 `instrument` 代码；
- 系统接入境外期货、期权或其他可能存在代码冲突的市场；
- 上游数据源只能使用 `exchange + instrument` 唯一标识合约；
- 单字段代码的全局唯一性无法在数据加载阶段可靠保证。

届时建议统一调整为：

```text
品种查询键：(exchange, product)
合约查询键：(exchange, instrument)
合约日频状态查询键：(exchange, instrument, trading_date)
```

该重构必须同时覆盖 API 参数、DataFrame 索引、内存缓存键、文件定位、
数据对象和一致性校验。仅在函数参数中增加 `exchange`，而缓存或索引仍
使用单字段键，不能真正解决跨交易所代码冲突。
