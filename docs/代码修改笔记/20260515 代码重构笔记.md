一、master_table 的持久化设计

第一， 在目前的设计中， create_research_feed 函数在每次组装时，都要先去构造一个换月总表(master_table)。
这一步涉及不少的计算量，不应该在向研究员输出内容时“动态计算”，而是应该“预加载全量”本地已准备好的数据。
也就是说, ContinousContractManager 应该在初始化时，应该加载本地的换月总表。
那么本地的换月总表从何而来？工业界的做法是“持久化”，弄一个ETL，每天收盘进行一次计算，保存品种的master_table，例如RB_master_table.csv或存入数据库。
（因此，为了模拟这一步，我们首先需要计算出一个本地的 master_table。在写代码时先假设我们有这么一个master_table。

注意，本地持久化的 master_table 和我们目前的设计有差异：
我们目前的设计是包含 Dominant_Contract, Price_Gap, Adj_Factor。
但是本地持久化的 master_table 不应该包含 Adj_Factor 这一列。因为如果包含，则每次换月，历史上的 Adj_Factor 都要改变，这使得我们会产生 master_table_20250514.csv, master_table_20250725.csv 这种每天都要存一个的窘境。
解决方案：删除 Adj_Factor 这一列。仅保留 Price_Gap，然后在 ResearchFeed 的 get_historical_vector 内部动态计算。

```python
#假设从 master_table 切片中取出了这期间的换月缺口列 Price_Gap
#动态计算【前复权因子】：从后往前累加（注意加减符号的具体业务定义）
#使用 [::-1] 倒序，cumsum() 累加，然后再 [::-1] 翻转回来
resampled_df['Adj_Factor'] = resampled_df['Price_Gap'].iloc[::-1].cumsum().iloc[::-1]

#如果需要，再平移一位，因为当天的 gap 影响的是历史所有天
resampled_df['Adj_Factor'] = resampled_df['Adj_Factor'].shift(-1).fillna(0)
```

二、 RolloverDetector 和 AdjustmentCalculator 的重构

（一）
首先，两者配合使用后，输出的内容是 master_table，即换月总表。而前者需要输出一个 rollover_calendar （换月日历）。
我们用一个简易的流程图来展示 (:之后，->之前，是函数的输入，->之后，是输出）：
RolloverDetector._build_oi_matrix(): -> oi_matrix
RolloverDetector.gen_rollover_calendar(): oi_matrix -> rollover_calendar[symbol_root, buffer_days, ratio_threshold]
AdjustmentCalculator._build_daily_close_matrix(): -> close_matrix[symbol_root]
AdjustmentCalculator.calculate_adjustment_factors(): rollover_calendar[symbol_root, buffer_days, ratio_threshold] + close_matrix[symbol_root] -> master_table[symbol_root, buffer_days, ratio_threshold] 

根据上述梳理，我们可以发现，master_table 有三个参数：symbol_root, buffer_days, ratio_threshold。
因此，我们有以以下几个需要注意的点：

1. 在持久化的 master_table 文件中，我们应该让其文件名包含参数，或将参数储存在数据文件本身里面——采用 Parquet 格式的优势（支持内部定义 key: value）。
  1.1. 设计一个生产的标准参数组，并配套相应的实验参数组，不同的参数生成的 master_table 分开存放。见下面的树状图。
        data/metadata/master_tables/
        ├── production/                # 生产/官方标准版
        │   └── RB.parquet             # 使用默认参数 (5, 0.8) 或叫做 RB_main.parquet
        └── research/                  # 研究/实验版
            ├── RB_b3_r70.parquet      # buffer=3, ratio=0.7
            └── RB_b10_r90.parquet     # buffer=10, ratio=0.9
2. 代码接口契约：ContinousContractManager 在初始化时，应该允许接收有默认值的 buffer_days 和 ratio_threshold，并根据某种指纹，加载相应的 master_table，若找不到则报错/触发计算，并提示。
    * 具体的实现：让其接收一个配置类 RolloverConfig 的实例。内部根据配置的指纹，搜寻相应的 master_table（换月日历）【在真正的生产级系统中，参数组可能很长，此时需要将整个配置对象序列化后计算 MD5 哈希值。但在我们目前的个人项目中，参数不多，用指纹命名，不会超过操作系统允许的文件名长度，直接用指纹法即可。】
    * 见下方更多的配置类设置——投研数据流的参数空间。

（二）
目前的 RolloverDetector 下有一个 _build_oi_matrix 方法， AdjustmentCalculator 下有一个 _build_daily_close_matrix 方法。这两个方法没有遵循解耦原则，直接在和硬盘打交道。
第一步，我们分析一下，_build_oi_matrix 方法，原料是什么，产出是什么？
原料： 关于某个品种（例如RB）的所有历史合约的 1min 数据文件。
产出： 日频的OI表。
注意到问题了吗？ 我们实际上只需要日频的数据源就可以了——RB的所有历史合约的数据。(实际上只需要未处理的新合约，但由于日频处理效率本身已经够高了，这里就用所有历史吧)

因此，关于这两个方法，我们有几处需要修改：

1. 写一个 DailyDataLoader（或者在 BarLoader 下写一个 load_daily_bar 方法），专门用于读取日频快照，或日频 K 线数据。典型的日频快照(Daily Summary Table)包含如下列：TradingDate, Contract, Close, Settlement, Volume, OpenInterest。这张表通常由交易所直接提供，称为每日结算数据MTM。

    * DailyDataLoader 下有 load_oi_history，load_close_history 方法。
    * 日频快照数据，按照每个品种一个 parquet 文件存储：
        data/
        └── storage/
            └── daily_snapshots/
                ├── RB_daily.parquet
                ├── CU_daily.parquet
                ├── IF_daily.parquet
                └── ...
    * DailyData 的使用放到 run_symbol_etl 里面去，不要放到 RollGapCalculator 里面。 切记，做到充分解耦。

三、投研数据流的参数空间

在一个工业级的量化系统中，为了生成一条可以让研究员用于回测的复权主力合约价格历史序列，我们应该有哪些，或称哪几组参数？

让我们称这些参数组为“配置对象”。总体而言，我们有以下几个：

1. RolloverConfig: buffer_days(换月缓冲天数), ratio_threshold(比例阈值)、transaction_days(换月过渡期窗口)。
2. AdjustmentConfig: direction(复权方向，包括 forward 和 backward )，method(复权计算方法，包括 additive 和 multiplicative)。
3. SamplingConfig: imputation_method(缺失值处理，例：如果某一根 15min K线全市场无成交（涨跌停时常见），是填补上一根收盘价 (ffill)，还是直接丢弃这行 (drop)), alignment(对齐模式，是否强制对齐标准的物理时间轴？防止因为某天提早收盘导致时间戳错位), include_night_session(夜盘开关，特定的日内动量策略需要屏蔽夜盘数据，只在日盘交易)。
4. EnvironmentConfig: data_source/data_dir（数据源，本地清洗好的，还是直接连生产数据库), max_caches_size(最大缓存数量，防止研究员在本地跑全品种回测时撑爆内存)。

对研究员而言，跑完策略，直接把 Config 实例序列化成 JSON 存进日志，未来随时精准复现。或者让系统支持跑完回测后，自动生成一个包含所有上下文（context）的JSON 或 YAML 文件。结构大致如下：

```JSON
{
  "experiment_id": "exp_20260514_1830",
  "symbol": "RB",
  "performance": {
    "sharpe_ratio": 2.1,
    "max_drawdown": -0.08,
    "annualized_return": 0.15
  },
  "context": {
    "data_generation_params": {
      "rollover_buffer_days": 5,
      "rollover_ratio_threshold": 0.8
    },
    "strategy_params": {
      "moving_average_fast": 10,
      "moving_average_slow": 50
    },
    "system_version": "v1.2.0"
  }
}
```
