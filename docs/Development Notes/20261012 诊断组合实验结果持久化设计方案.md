# 诊断组合实验结果持久化设计方案

## 1. 文档目的

本文定义 `factors/diagnostic_portfolio` 层研究结果持久化的 V1 方案，作为后续编码、测试和演进的依据。

本方案承接：

- [《因子研究闭环与组合实验层开发方向》](<./20260924 因子研究闭环与组合实验层开发方向.md>)；
- [《组合实验层组件开发方案》](<./20260924 组合实验层组件开发方案.md>)。

本方案优先满足个人研究项目的实际需要：

1. 一次组合实验的实际输入和输出可追溯；
2. 已保存的组合实验可以脱离后来发生变化的本地数据库重新加载和复跑；
3. 能识别运行时采用的代码版本和数据边界；
4. 初期保持文件式存储，不引入服务、外部数据库、对象存储、DVC 或 MLflow；
5. 文件结构和 manifest 为以后按参数查询、共享输入快照和建立 SQLite 索引保留扩展空间。

本文只设计持久化边界，不改变组合权重、收益核算、归因和绩效计算逻辑。

---

## 2. 核心结论

V1 采用“不可覆盖的运行目录 + JSON manifest + Parquet 表格”的文件式存储方案。

代码放在：

```text
factors/diagnostic_portfolio/storage/
```

实验产物默认放在：

```text
research/artifacts/diagnostic_portfolio/runs/
```

`research/artifacts/` 已由仓库 `.gitignore` 忽略，适合保存本地研究产物。存储根目录必须允许调用方注入，默认路径只提供便利，不写入领域对象，也不复用 `EnvironmentConfig` 表达研究产物路径。

V1 的权威记录包括：

- `manifest.json`：配置、身份、来源、环境、校验和和文件目录；
- `inputs/experiment_panel.parquet`：组合实验实际消费的已对齐输入；
- 必要时保存 `inputs/auxiliary/` 下实际消费的附属输入；
- `outputs/*.parquet`：`DiagnosticPortfolioResult` 的全部表格结果。

V1 不把持久化做成 `DiagnosticPortfolioExperimentRunner.run()` 的隐式副作用。研究流程应先得到结果，再显式调用 Store 保存。

## 3. 为什么配置本身不足以复现

从领域概念看，一次研究由以下三组配置描述：

- `DatasetSpec`；
- `DiagnosticSignal.recipe`；
- `DiagnosticPortfolioSpec`。

但是当前运行器的实际输入是：

```python
DiagnosticPortfolioExperimentRunner(
    signal=signal,
    dataset=dataset,
    spec=spec,
)
```

其中会真实参与计算的是：

- `DiagnosticSignal.values`；
- `ResearchDataset.main_panel['True_Return']`；
- `ResearchDataset.universe.eligible`；
- 被组合实验使用的 `ResearchDataset.auxiliary` 子集；
- `DiagnosticPortfolioSpec`。

`DatasetSpec` 是数据请求意图，不是已解析的数据快照。例如：

- `start_date=None` 和 `end_date=None` 会随数据库增长而改变实际样本；
- 数据文件可能修订历史记录，但最大业务日期保持不变；
- 动态品种池依赖当时的行情和规则数据；
- 相同 recipe 在底层数据变化后可能产生不同信号；
- recipe 记录不完整时，不能仅靠配置重建信号。

因此，V1 同时保存配置和组合层实际输入。配置回答“希望做什么”，输入快照回答“这次实际上计算了什么”。

## 4. 复现范围

### 4.1 V1 保证：组合实验层复现

V1 保存 `align_inputs()` 形成的稳定排序长表：

```text
Index[timestamp, product]
columns = true_return, eligible, signal
```

该表是组合权重状态机和收益核算的核心实际输入。若启用了板块归因，还应保存实际使用的分类数据子集。

在配置、代码和这些输入不变时，应能重新构建组合实验所需的最小输入并得到相同结果。复跑时不再向当前本地数据库重新请求历史数据。

### 4.2 V1 记录但不保证：从原始数据库重建全部上游过程

V1 保存 `DatasetSpec`、信号 recipe、数据截止时间和可获得的数据来源说明，但不为所有原始行情、规则数据和基本面数据建立全库快照。

因此，V1 可以：

- 审计当时请求了什么数据；
- 审计当时实际进入组合实验的值；
- 检测存储产物是否被修改；
- 精确复跑组合实验层。

但在底层数据库被覆盖后，V1 不承诺从原始数据库重新生成完全相同的 `ResearchDataset` 和信号。以后可通过不可变数据快照或内容寻址的数据版本补足这一能力。

### 4.3 复现状态必须显式表达

manifest 应提供复现状态，而不是笼统地声明“可复现”：

```text
strict
    输入快照完整，代码来自干净且可定位的 Git commit。

input_replayable_code_dirty
    输入快照完整，但运行时工作区包含未提交代码；可审计、可加载，
    不能只依靠 commit 严格恢复执行代码。

incomplete
    缺少必需输入或来源信息。正常完成的 V1 save 不应产生此状态。
```

工作区不干净不阻止个人研究保存结果，但必须降低复现等级并给出明确警告。

## 5. 职责边界

### 5.1 Runner 的职责

`DiagnosticPortfolioExperimentRunner` 继续只负责：

- 输入对齐；
- 权重计算；
- 收益和成本核算；
- 风险、暴露、归因和绩效计算；
- 返回 `DiagnosticPortfolioResult`。

Runner 不负责：

- 创建运行目录；
- 获取 Git 信息；
- 写 JSON 或 Parquet；
- 判断缓存命中；
- 自动覆盖或删除旧实验。

### 5.2 Store 的职责

`DiagnosticPortfolioStore` 负责：

- 建立运行身份；
- 规范化并序列化配置；
- 构造和保存组合实验实际输入；
- 保存完整结果；
- 生成 manifest 和文件校验和；
- 原子发布一个完整运行目录；
- 加载并校验已保存运行；
- 扫描 manifest 提供轻量查询。

Store 不负责重新计算研究指标，也不在加载时修补、推断或升级结果值。

### 5.3 调用方的职责

notebook、研究脚本或未来的实验编排器负责决定：

- 哪次运行需要保存；
- 可选的标签、研究备注和数据来源说明；
- 是否接受 `git_dirty=true` 的非严格复现实验；
- 是否在加载后执行复跑比对。

## 6. 代码目录设计

V1 推荐目录：

```text
factors/
    diagnostic_portfolio/
        __init__.py
        models.py
        experiment.py
        accounting.py
        risk.py
        weights.py
        storage/
            __init__.py
            store.py
            serialization.py
            models.py

tests/
    factors/
        diagnostic_portfolio/
            storage/
                test_store.py
                test_serialization.py
```

职责如下：

- `storage/store.py`
  - `DiagnosticPortfolioStore` 公共入口；
  - 运行目录管理；
  - 保存、加载、校验和轻量查询；
  - 临时目录与原子发布。
- `storage/serialization.py`
  - 配置对象与 JSON 基础类型之间的显式转换；
  - pandas 对象与 Parquet 之间的转换；
  - 规范 JSON 和 SHA-256 辅助函数。
- `storage/models.py`
  - `RunManifest`、`ArtifactRecord`、`StoredDiagnosticPortfolioRun`、`RunSummary` 等存储层对象；
  - 存储 schema 的字段约束。
- `storage/__init__.py`
  - 仅导出稳定公共接口。

如果首次编码规模很小，可以暂时把 `models.py` 和 `serialization.py` 的实现放在 `store.py`，但公共概念和职责仍按以上边界设计；文件明显膨胀后再机械拆分，不创建无内容的空壳模块。

存储模型属于基础设施，不加入现有 `factors/diagnostic_portfolio/models.py`。后者继续只承载组合实验领域对象。

## 7. 公共接口

V1 建议的最小接口为：

```python
store = DiagnosticPortfolioStore(
    root_dir='research/artifacts/diagnostic_portfolio'
)

run_id = store.save(
    dataset=dataset,
    signal=signal,
    spec=spec,
    result=result,
    note='动量 15 日、每 10 日调仓',
    tags=('momentum', 'baseline'),
    data_provenance=None,
)

stored = store.load(run_id, verify=True)

runs = store.find(
    signal_name='momentum_15',
    harvest_profile='market_rank_ls',
)
```

具体类型建议：

```python
class DiagnosticPortfolioStore:
    def save(...) -> str: ...
    def load(self, run_id: str, *, verify: bool = True) \
            -> StoredDiagnosticPortfolioRun: ...
    def find(self, **filters: object) -> tuple[RunSummary, ...]: ...
```

V1 的 `find()` 只扫描完整运行目录中的 manifest，不建立中心索引。过滤器只支持文档明确列出的常用字段和精确匹配；不接受任意代码、表达式或 SQL。

`save()` 是显式操作：

```python
result = runner.run()
run_id = store.save(dataset, signal, spec, result)
```

不采用：

```python
result = runner.run(save=True)
```

这样测试 Runner 时不会产生文件副作用，计算失败也不会留下伪装成完整结果的运行目录。

## 8. 产物目录结构

一次成功运行的目录如下：

```text
research/artifacts/diagnostic_portfolio/
    runs/
        20261012T153012_123456_a13f9c26/
            manifest.json
            inputs/
                experiment_panel.parquet
                auxiliary/
                    classification.parquet
            outputs/
                target_weights.parquet
                rebalance_flags.parquet
                weight_changes.parquet
                turnover.parquet
                decision_cost.parquet
                product_contributions.parquet
                portfolio_returns.parquet
                nav.parquet
                exposures.parquet
                risk.parquet
                product_attribution.parquet
                direction_attribution.parquet
                sector_attribution.parquet
                performance.parquet
                status.parquet
                metadata/
                    root_covariance_estimation.parquet
```

其中可选或值为 `None` 的结果不创建空 Parquet；manifest 中仍保留对应 artifact 记录，并标记 `present=false`。

运行目录发布后视为不可变：

- 不覆盖同名目录；
- 不在原目录中追加新结果；
- 备注修改也通过新版本机制或单独的用户注释层完成，V1 不提供原地编辑；
- 重新运行产生新的 `run_id`。

### 8.1 为什么使用 `experiment_panel.parquet`

`experiment_panel.parquet` 保存 `align_inputs()` 的输出，而不是复制整个 `ResearchDataset.main_panel`。它只包含组合实验实际使用的：

```text
true_return
eligible
signal
```

优点是：

- 直接对应当前组合实验的计算边界；
- 避免保存大量本层不使用的 OHLC、成交量和持仓量字段；
- 同时避免 `signal.parquet` 和另一份包含 signal 的输入表重复；
- 后续复跑不依赖当前数据库，也不需要重做因子计算。

如果未来 Runner 消费新的主面板字段，必须同步提高 manifest schema 版本并扩展该输入表，不能静默依赖未保存数据。

### 8.2 附属数据

只有真正被本次实验消费的附属数据才保存。例如：

- `sector_attribution_col is not None` 且运行时确实执行板块归因时，保存对应分类数据；
- 未使用的 term structure、仓单原始表等不因它们存在于 `ResearchDataset.auxiliary` 就自动复制。

manifest 必须记录附属数据用途、字段、索引结构和对应 artifact。

## 9. Manifest 设计

### 9.1 顶层结构

V1 manifest 建议采用以下结构：

```json
{
  "schema_version": 1,
  "run_id": "20261012T153012_123456_a13f9c26",
  "created_at": "2026-10-12T15:30:12.123456+08:00",
  "status": "complete",
  "reproducibility_level": "strict",
  "identity": {},
  "configs": {},
  "resolved_input": {},
  "code_provenance": {},
  "data_provenance": {},
  "runtime": {},
  "artifacts": {},
  "warnings": [],
  "result_metadata": {},
  "user_metadata": {}
}
```

`schema_version` 是存储格式版本，不是业务代码版本。加载器遇到高于自身支持范围的版本时必须明确报错，不得尽力猜测。

### 9.2 identity

至少包含：

```json
{
  "config_fingerprint": "sha256:...",
  "input_fingerprint": "sha256:...",
  "experiment_fingerprint": "sha256:..."
}
```

- `config_fingerprint`：规范化后的语义配置哈希；
- `input_fingerprint`：本次实际输入 artifact 校验和按稳定顺序组合后的哈希；
- `experiment_fingerprint`：配置指纹、输入指纹和代码来源组合后的哈希。

`run_id` 表示一次保存事件，`experiment_fingerprint` 表示研究内容身份，两者不能混用。相同研究可以重复执行并产生不同 `run_id`。

当 `git_dirty=true` 时，`experiment_fingerprint` 仍可用于本地比对，但不得被解释为足以恢复执行代码的严格身份。

### 9.3 configs

至少保存：

```json
{
  "dataset_spec": {},
  "signal": {
    "name": "momentum_15",
    "source_stage": "raw",
    "factor_name": "momentum",
    "recipe": {},
    "warnings": {}
  },
  "diagnostic_portfolio_spec": {}
}
```

`DiagnosticSignal.values` 不写进 JSON，由 `experiment_panel.parquet` 承载。

`HarvestProfile` 必须保存完整字段，不能只保存 `name`。同名 profile 的其他字段以后可能发生变化，完整快照才能解释旧实验语义。

`DatasetSpec` 中的 `EnvironmentConfig` 路径需要保存在 manifest 中用于审计，但机器路径不进入 `config_fingerprint` 的语义配置部分。相同数据和研究参数只因换了本地目录，不应被识别为不同研究假设。

### 9.4 resolved_input

记录实际输入事实，而不只是请求配置：

```json
{
  "products": ["A", "AG", "AL"],
  "start_timestamp": "2010-01-04T00:00:00",
  "end_timestamp": "2026-10-09T00:00:00",
  "row_count": 123456,
  "timestamp_count": 4088,
  "product_count": 72,
  "signal_non_null_count": 110000,
  "eligible_true_count": 95000,
  "index_names": ["timestamp", "product"],
  "columns": ["true_return", "eligible", "signal"]
}
```

这里的起止时间和品种集合来自已对齐实际输入，不从 `DatasetSpec` 直接照抄。

### 9.5 code_provenance

至少保存：

```json
{
  "git_commit": "完整 40 位 commit",
  "git_dirty": false,
  "git_diff_sha256": null,
  "untracked_source_files": []
}
```

规则如下：

- Git commit 使用完整哈希，不只保存短哈希；
- 工作区干净时，commit 是 V1 的代码版本；
- 工作区不干净时，记录相对 `HEAD` 的 diff 哈希用于识别变化；
- 未跟踪的 Python 文件单独列出；
- V1 不自动保存或应用补丁，也不把未跟踪文件内容写入研究产物；
- 只要工作区不干净，复现等级就不能为 `strict`。

Git 信息获取失败时，不伪造 `unknown` commit。可以允许保存，但必须将失败原因写入 warnings，并降低复现等级。

### 9.6 data_provenance

需要明确区分：

- `captured_at`：Store 保存输入快照的时间；
- `logical_data_cutoff`：实际消费数据的最大业务时间；
- `source_as_of`：调用方或上游 Builder 能够提供的各数据源截止信息；
- `input_fingerprint`：已保存实际输入的内容身份。

示例：

```json
{
  "captured_at": "2026-10-12T15:30:12.123456+08:00",
  "logical_data_cutoff": "2026-10-09T00:00:00",
  "source_as_of": {
    "main_panel": "2026-10-09",
    "warehouse_receipt": "2026-10-08"
  }
}
```

“数据库最新时间”只能作为 `source_as_of` 或 `logical_data_cutoff`，不能单独称为数据版本。历史数据可能在最大日期不变时被修订。V1 的严格组合层复现依靠输入快照，数据截止时间用于人类审计。

Store 不应通过遍历 `EnvironmentConfig` 中的全部目录猜测数据来源。上游暂时无法提供 `source_as_of` 时可以为空，但 `logical_data_cutoff` 必须根据实际输入生成。

### 9.7 runtime

V1 保存影响读取和数值复现的最小运行环境：

```json
{
  "python": "3.12.x",
  "platform": "Windows-...",
  "packages": {
    "numpy": "...",
    "pandas": "...",
    "pyarrow": "..."
  }
}
```

不生成或维护 `requirements.txt`、`pyproject.toml` 或完整环境锁文件。运行环境仍遵守仓库使用 Conda base 环境的约定。

### 9.8 artifacts

每个 artifact 至少记录：

```json
{
  "path": "outputs/nav.parquet",
  "format": "parquet",
  "kind": "dataframe",
  "present": true,
  "sha256": "...",
  "size_bytes": 12345,
  "row_count": 4087,
  "column_count": 2,
  "index_names": ["timestamp"],
  "columns": ["gross_nav", "proxy_net_nav"],
  "dtypes": ["float64", "float64"],
  "index_dtypes": ["datetime64[ns]"]
}
```

Series 统一以单列 DataFrame 写入 Parquet，同时记录：

```json
{
  "kind": "series",
  "series_name": "turnover"
}
```

加载器据此恢复为 Series，不能仅根据“只有一列”猜测对象类型。

Parquet 可能把原本为 `object`、但内容恰好全是 Timestamp 的列推断为
datetime dtype。因此 artifact 还必须记录原始列与索引 dtype；加载时先按记录恢复
dtype，再执行 round-trip 结构校验，不能只比较数值。

文件校验和均在文件写完后计算，采用 SHA-256。校验和首先用于完整性验证；V1 不依赖 Parquet 字节哈希实现跨版本去重。

### 9.9 warnings、result_metadata 和 user_metadata

- `warnings` 保存 `DiagnosticPortfolioResult.warnings`；
- `result_metadata` 保存 `DiagnosticPortfolioResult.metadata`；
- `storage_warnings` 保存 Git 信息不可用、recipe 为空等持久化审计警告；
- `user_metadata` 保存可选的 `note`、`tags` 等研究者信息。

`DiagnosticPortfolioResult.metadata` 当前可能包含 DataFrame，例如目标波动率范式的
协方差估计元数据。此类表格不转成字符串，也不塞进 JSON；存储器把它拆到
`outputs/metadata/*.parquet`，并在 `result_metadata` 中保存受校验的 artifact 引用，
加载时递归恢复原 Mapping 结构。

以上字段分开存放，避免把计算事实、计算警告、存储警告和研究者备注混成一个没有
语义边界的字典。

## 10. JSON 序列化规则

不能直接假设 `dataclasses.asdict()` 的结果一定可由 JSON 正确表达。V1 实现显式、递归、拒绝未知类型的规范化序列化器。

允许类型及规则：

| Python 类型 | JSON 表达 |
|---|---|
| `None`、`bool`、`str`、`int` | 原生值 |
| 有限 `float` | JSON number |
| `date`、`datetime`、`pd.Timestamp` | ISO 8601 字符串 |
| tuple、list | JSON array |
| 字符串键 Mapping | 按键排序后的 JSON object |
| dataclass | 显式类型 codec 转换后的 object |
| NumPy 标量 | 转成对应 Python 标量 |
| `Path` | 规范字符串，仅用于审计字段 |

额外规则：

- JSON 使用 UTF-8；
- 输出固定缩进并设置稳定键顺序；
- 禁止 NaN 和正负无穷写入 JSON；
- 禁止把未知对象静默转换成 `repr(obj)`；
- 遇到无法表达的 recipe 或 metadata 时，`save()` 明确失败并指出字段路径；
- 禁止使用 pickle 作为任何配置或结果的权威格式。

反序列化采用已知类型的显式 codec 注册表，不根据 JSON 中的任意 import path 动态导入和实例化对象。recipe 中的类路径只是研究说明，不是反序列化执行指令。

---

## 11. Parquet 序列化规则

### 11.1 通用要求

- pandas 表格统一使用 Parquet；
- 保存前不原地修改调用方对象；
- 保留索引、索引层级名称、列名和可恢复 dtype；
- 保存前按各领域对象已经定义的稳定顺序写出，不额外改变经济含义；
- Series 先转为单列 DataFrame，再写 Parquet；
- artifact 记录原对象种类、Series 名称、列 dtype 和索引 dtype；
- 加载后执行结构校验。

### 11.2 空表与 `None`

- 空 DataFrame 或空 Series 是“存在但为空”，应写出文件并记录 `present=true`；
- `None` 是“不适用或未产生”，不写文件并记录 `present=false`；
- 两者不能混淆。

当前 `DiagnosticPortfolioResult.status` 的类型声明为 DataFrame，但 Runner 的实际构建路径可能传入 `None`。V1 存储 schema 应按可选结果处理；后续代码实现时宜同步修正领域类型标注，使声明和运行行为一致。该差异不阻塞本方案。

### 11.3 浮点一致性

V1 的 round-trip 测试要求加载后的 pandas 对象与保存前对象在值、索引、列和 dtype 上一致。

不同 pandas、NumPy 或 PyArrow 版本重新执行计算时，底层浮点舍入可能出现极小差异。因此“复跑结果一致”分为：

- 存储 round-trip：要求精确相等；
- 重新计算比对：浮点字段使用明确的 `rtol`、`atol`，索引、列、布尔值和缺失位置要求精确相等。

容差由复跑验证函数统一定义，不散落在测试和 notebook 中。

## 12. 运行身份

### 12.1 run_id

建议格式：

```text
YYYYMMDDTHHMMSS_microseconds_<fingerprint前8位>
```

例如：

```text
20261012T153012_123456_a13f9c26
```

时间使用带时区的当前时间生成，目录名采用不含冒号和时区符号的安全形式；完整带时区时间保存在 manifest。

如果极低概率发生目录名冲突，应重新生成唯一后缀，不能覆盖现有运行。

### 12.2 config_fingerprint

配置指纹基于 canonical JSON 计算。纳入：

- `DatasetSpec` 中影响数据含义的字段；
- 完整 signal 描述和 recipe；
- 完整 `DiagnosticPortfolioSpec` 和 `HarvestProfile`。

排除：

- `EnvironmentConfig` 中只表示本地物理位置的路径；
- 运行时间；
- note 和 tags；
- 输出结果；
- 文件名和运行目录。

路径字段虽然不进入语义指纹，仍完整保存在 manifest 供审计。

### 12.3 experiment_fingerprint

实验指纹由以下内容按固定顺序组合：

```text
schema_version
config_fingerprint
input_fingerprint
git_commit
git_dirty
git_diff_sha256
```

它用于识别和比较，不在 V1 中触发自动缓存命中或跳过计算。将“持久化仓库”升级为“计算缓存”需要单独设计缓存有效性、失败恢复和并发锁，不能由指纹存在就自动推导。

## 13. 原子写入和不可变性

### 13.1 保存流程

`save()` 应按以下顺序执行：

1. 校验输入对象类型和基本关联关系；
2. 生成规范配置和实际输入表；
3. 在 `runs/` 下创建仅属于本次调用的临时目录；
4. 写入输入和输出 Parquet；
5. 重新读取关键文件，验证基本结构；
6. 计算每个文件的 SHA-256、大小和表格摘要；
7. 构建完整 manifest；
8. 最后写入临时目录中的 `manifest.json`；
9. 将临时目录原子改名为最终 `run_id` 目录；
10. 返回 `run_id`。

最终目录存在即表示已完整发布，`manifest.status` 必须为 `complete`。

### 13.2 保存失败

- 失败时不得创建同名最终运行目录；
- 临时目录可以保留用于排查，也可以由明确的清理接口删除；
- `find()` 和正常 `load()` 不扫描临时目录；
- V1 不建立 `running`、`failed` 运行记录，因为 Store 只在 Runner 已成功返回结果后调用；
- 未来实验编排器若需要记录失败运行，应另行扩展 lifecycle schema。

### 13.3 不可覆盖

最终运行目录不可覆盖。Store 不提供 `overwrite=True`。

删除实验属于破坏性管理操作，不放入 V1 最小公共接口。以后增加时必须要求明确 `run_id`，并与保存、加载接口分离。

---

## 14. 加载与校验

`load(run_id, verify=True)` 的默认行为：

1. 校验 `run_id` 是单个安全目录名，禁止路径穿越；
2. 读取 manifest；
3. 校验支持的 `schema_version`；
4. 校验 `status == 'complete'`；
5. 校验所有 `present=true` 的 artifact 存在；
6. 校验路径都位于该运行目录内；
7. 重新计算 SHA-256 并与 manifest 比较；
8. 按 artifact 中的 `kind` 恢复 Series 或 DataFrame；
9. 校验索引名称、列名、行数等结构摘要；
10. 通过显式 codec 恢复领域配置；
11. 返回 `StoredDiagnosticPortfolioRun`。

建议返回对象包含：

```python
@dataclass(frozen=True)
class StoredDiagnosticPortfolioRun:
    manifest: RunManifest
    result: DiagnosticPortfolioResult
    experiment_panel: pd.DataFrame
    auxiliary_inputs: Mapping[str, pd.DataFrame | pd.Series]
```

默认校验完整性优先于加载速度。以后如大批量查看摘要，应使用 `find()` 只读 manifest，而不是 `load(verify=False)` 读取全部表格。

## 15. 轻量查询

### 15.1 V1 查询方式

V1 遍历：

```text
runs/*/manifest.json
```

只返回 `status=complete` 且 schema 可识别的运行。常用过滤字段包括：

- `run_id`；
- 创建时间范围；
- `signal_name`；
- `factor_name`；
- `source_stage`；
- `harvest_profile.name`；
- `DatasetSpec.products`；
- 实际起止时间；
- `git_commit`；
- `config_fingerprint`；
- `experiment_fingerprint`；
- tags。

结果按 `created_at`、`run_id` 稳定排序。

参数查询首先从已规范化 manifest 读取，不解析目录名，不读取 Parquet。

### 15.2 后续 SQLite 索引

当运行数量使 manifest 扫描变慢时，可增加：

```text
research/artifacts/diagnostic_portfolio/catalog.sqlite
```

SQLite 只保存查询所需的扁平字段和 manifest 路径，权威记录仍是各运行目录。索引必须能够从 manifest 全量重建，因此索引损坏或删除不能造成实验丢失。

V1 不实现 SQLite，也不维护一个需要并发追加的总 CSV 或总 Parquet 索引。

## 16. 信号 recipe 约定

recipe 应是可序列化的声明式快照，至少能解释因子构造参数和预处理顺序。例如：

```json
{
  "factor": {
    "class": "factors.library.momentum.MomentumFactor",
    "params": {
      "lookback": 15
    }
  },
  "preprocess": []
}
```

有预处理时：

```json
{
  "factor": {
    "class": "...",
    "params": {}
  },
  "preprocess": [
    {
      "class": "...RollingTimeseriesWinsorizer",
      "params": {}
    },
    {
      "class": "...FittedTimeSeriesZscore",
      "params": {}
    }
  ]
}
```

V1 不把 recipe 解释为可执行代码，也不要求 Store 根据 recipe 自动实例化因子。recipe 用于审计和未来的上游复建；`experiment_panel.parquet` 中的 signal 列才是本次组合实验实际消费的权威信号值。

当前 notebook 中存在空 recipe。Store 可以保存空 recipe，但应在 manifest warnings 中加入“信号配方为空，上游信号不可仅靠配置重建”的警告，不因此拒绝组合层快照保存。

## 17. 错误政策

建议定义存储层异常基类和清晰子类：

```text
DiagnosticPortfolioStorageError
    SerializationError
    ManifestValidationError
    ArtifactIntegrityError
    UnsupportedSchemaVersionError
    RunNotFoundError
    RunAlreadyExistsError
```

错误政策：

- 无法 JSON 序列化的配置、recipe、warnings 或 metadata：保存失败；
- 非有限 JSON 浮点值：保存失败并报告字段路径；
- 必需结果字段缺失：保存失败；
- 可选字段为 `None`：正常记录 `present=false`；
- 文件校验和不一致：加载失败，不自动忽略；
- manifest 与 Parquet 结构摘要不一致：加载失败；
- 未知 schema 版本：加载失败；
- Git 信息不可用：允许保存、记录警告、降低复现等级；
- 空 recipe：允许保存、记录警告；
- 已存在的最终 `run_id`：不覆盖，生成新 ID 或明确失败。

Store 不吞掉异常后返回部分 `DiagnosticPortfolioResult`。

---

## 18. 安全与可移植性

- 禁止 pickle，避免任意代码执行和版本脆弱性；
- manifest 中 artifact 路径必须是相对运行目录的正向路径；
- 加载时解析后的绝对路径必须仍在目标运行目录内；
- `run_id` 不接受路径分隔符、`.` 或 `..`；
- recipe 中的类路径不触发动态 import；
- 不在 manifest 中保存 API 凭证、环境变量全集或用户主目录内容；
- `EnvironmentConfig` 中的本地路径只用于审计，跨机器加载结果不要求这些路径存在；
- JSON 统一使用 UTF-8；
- 时间写入 ISO 8601，运行创建时间必须带时区；
- Parquet schema 和 manifest schema 共同决定恢复方式。

## 22. 后续扩展方向

V1 稳定后，可按实际需要依次扩展：

1. 内容寻址的共享输入快照，减少相同 dataset 在多次参数实验中的重复存储；
2. SQLite 可重建查询索引；
3. 上游 Dataset Builder 输出来源文件清单和数据指纹；
4. 不可变原始数据版本或快照引用，实现从原始数据开始的全链路复现；
5. 保存脏工作区补丁或要求正式研究必须使用干净 commit；
6. 实验生命周期记录，包括 running、failed 和 cancelled；
7. 基于严格指纹的缓存复用；
8. 统一因子统计诊断与组合实验的研究结果仓库；
9. 报告层只消费已保存结果生成标准表格和 tear sheet；
10. 对象存储或远程研究产物同步。

这些扩展不得改变 V1 的核心事实：每个最终运行目录自描述、可校验，manifest 是查询入口，输入和结果 artifact 才是本次实验实际数值的权威记录。

## 23. 最终边界

本方案把一次诊断组合实验拆成四个互相连接但职责不同的部分：

```text
配置
    描述希望运行什么

实际输入快照
    记录这次真正计算了什么

结果 artifacts
    记录这次得到了什么

manifest
    连接配置、输入、结果、代码和数据来源
```

V1 选择文件式、显式和不可变的设计，优先保证研究可信度，同时避免过早建设通用实验平台。未来无论增加参数查询、共享数据快照还是缓存，均应在这一边界上增量演进。
