## 一、背景与动机

### 1.1 现有接口

`DataFacade` 目前提供两条获取复权主连历史价格的路径：

| 接口 | 调度方式 | 任务粒度 |
|---|---|---|
| `get_historical_vector` | 无（调用方自己循环） | 单品种 |
| `get_historical_vector_multiple_products` | 无（内部串行循环） | 单品种一任务 |

> **变更记录（2026-10-05）**：本文档初稿时 `get_historical_vector_multiple_products` 为
> `ThreadPoolExecutor` 版本。经 §1.2 实测确认线程版无收益后，**该方法已直接改为串行实现**，
> `max_workers` 参数一并移除。`get_term_structure_data_multiple_products` 与
> `get_warehouse_receipt_data_multiple_products` 同步改为串行。下文凡提及「线程版」处，
> 均指改造前的历史状态；现存接口是串行版。

### 1.2 线程版实测结论：没有加速，反而更慢

在「全 94 品种 / 全量日期 / `freq='1d'` / 输出 252,593 行」的负载下实测，线程版**在任何 worker 数下都不如串行**：

| 测量时点 | 串行 | 线程 w=8 | 线程 w=16 | 线程 w=32 |
|---|---|---|---|---|
| 换月总表热点优化**前**（独立进程交错测量，中位） | 73.00s | 78.06s | 77.57s | 83.72s |
| 换月总表热点优化**后**（热态，中位） | 7.47s | 8.71s | 9.51s | 9.47s |

两个测量时点结论一致：**慢 6%–27%**。根因在 `cpu/wall ≈ 1.0–1.1`——该负载是纯 GIL 内的 Python CPU 计算，真实 parquet 解压 I/O 占比极小，GIL 使线程无法并行。

> 注：最终版代码（含 `_build_daily_lookup()` 优化）**尚未复测线程版**，因为当前阶段明确不测并行接口。若要给出「线程 vs 进程」的同基准对比，需补一次复测。

### 1.3 串行基线的当前水位

`ContinuousContractManager._build_daily_lookup()` 落地后（把换月总表逐交易日判定的 O(n²) 降为 O(1) 查表 + ndarray 缓存），串行基线从 73.00s 降到 **14.40s**（6 次独立进程测量，区间 13.09–15.42s，中位 14.40s）。这个水位是多进程方案的对比基准。

## 二、已确认的需求边界

| # | 决策项 | 结论 |
|---|---|---|
| 1 | worker 函数位置 | 新建 `data/parallel_fetcher.py`，**只放 worker 与其任务构造**，不放 facade 逻辑 |
| 2 | 现有线程版 | **去掉线程调度，改为串行**——即本接口不再自行调度，`max_workers` 一并移除；返回契约、异常包装保持不变 |
| 3 | 入口 | `DataFacade` 上**新增**一个方法 |
| 4 | 配置传递 | 子进程重建 `DataFacade` 时使用**调用方那个 facade 实例当初被传入的四个 config**，不得硬编码默认值 |
| 5 | 单品种失败语义 | **方案 A（fail fast）**：任一品种异常 → 整个调用抛出 |
| 6 | 任务粒度 | **每 chunk 一任务 + 静态 LPT 切分**（依据见第八章实测） |
| 7 | 覆盖范围 | **只做 `get_historical_vector`**。`get_term_structure_data`、`get_warehouse_receipt_data`、`get_market_event_stream` 一律不做多进程版本 |

### 2.1 明确不做（Non-Goals）

- 保留「线程 vs 进程」两条路径的对比数据（§1.2）作为决策依据，但不再保留线程版实现：既然线程比串行慢，中间态没有存在价值。
- 不引入新依赖（不引入 `psutil` 探测物理核数——已确认全仓库无任何 `psutil` 使用）。
- 不引入常驻进程池（一次性调用是本方案的边界，常驻属后续议题，见第十一章）。
- 不做跨 `DataFacade` 实例的配置覆盖能力：子进程配置完全跟随父 facade。
- 不把 worker 函数做成通用注册表 / 插件（本阶段只有一个 worker）。

## 三、性能基线与目标

### 3.1 多进程一次性调用（最终版代码，全 94 品种，全量日期，日频）

串行与多进程在同一进程内交替执行以抵消机器负载漂移。环境：16 物理核 / 22 逻辑核 / 33.8 GB RAM。

| 方案 | 总耗时 | 相对串行 | 备注 |
|---|---|---|---|
| 串行 | 12.81s–13.03s | 1.00x | 区间 11.02–15.42s，随页缓存热度变化 |
| 多进程（默认 w=11） | 4.83–4.87s | **2.63–2.70x** | 本方案默认值 |

**目标：默认配置下稳定达到 2.6x 以上。**

关于基线热度的说明：冷页缓存下串行为 14.40s、热页缓存下为 11.02s，而并行侧在两种状态下几乎不变（5.22s / 4.87s）。也就是说**多进程的收益在冷缓存时更大**——它把冷启动的 I/O 读取分散到多个进程，串行则要自己承担全部冷读惩罚。因此报出的加速比区间为 2.2x–2.8x，取决于当时的缓存状态。

### 3.2 并行度曲线：为什么默认不是 `os.cpu_count()`

同进程内交替测量，4 轮中位（串行基线 11.99s）：

| worker 数 | 中位耗时 | 相对串行 | 说明 |
|---|---|---|---|
| 4 | 6.59s | 1.82x | 并行度不足 |
| 6 | 5.67s | 2.12s | 进入平台 |
| 8 | 5.32s | 2.25x | 平台 |
| 10 | 5.33s | 2.25x | 平台 |
| **12** | **5.19s** | **2.31x** | **峰值** |
| 16 | 5.38s | 2.23x | 平台右端（= 物理核数） |
| **22** | **6.33s** | **1.89x** | **= `os.cpu_count()`，落在平台之外** |

**8~16 是平坦的高效平台。** 直接用 `os.cpu_count()`（本机 22）会损失约 18%。

物理机制：本负载受内存带宽限制，超线程兄弟核不增加吞吐，因此有效并行度对应**物理核数**而非逻辑核数。worker 实际计算耗时合计随进程数膨胀（串行单份 13.8s → 8 进程 22.67s（+64%）→ 16 进程 26.68s（+93%）→ 22 进程 33.74s（+144%）），这是超过物理核数后收益不再增长甚至倒退的原因。

在无新依赖的前提下无法探测物理核数，故按 2:1 超线程比例取逻辑核数的一半作为保守默认（本机得 11，落在平台正中）。该比例是在单台机器上标定的**启发式，不是通用结论**，需精细控制时由调用方显式传 `max_workers`。

### 3.3 一次性 vs 常驻的差距

| 方案 | 含启动 | 稳态（第 2 轮） | 稳态加速比 |
|---|---|---|---|
| w=8 | 4.59s | 3.41s | 4.22x |
| w=16 | 5.00s | 2.49s | **5.78x** |
| w=22 | 5.52s | 2.54s | 5.67x |

差距来源：w=16 时 worker 实际计算合计仅 26.68s / 16 ≈ 1.67s，而池内耗时 4.92s。差额约 2.5s 是 Windows `spawn` 拉起 16 个解释器并各自 import pandas/pyarrow 的成本（裸进程池实测冷启动 1.21s @16 worker，常驻后 IPC 往返仅 0.004s）。

**一次性调用摊不掉这 2.5s，这是本方案的固有限制。**

### 3.4 内存代价

整棵进程树峰值 RSS：

| 方案 | 峰值 | 同时进程数 |
|---|---|---|
| 串行 | 908 MB | 1 |
| 多进程 w=4 | 1,400 MB | 5 |
| 多进程 w=8 | 2,009 MB | 9 |
| 多进程 w=16 | **3,189 MB** | 17 |

约 3.5x。当前机器无压力；16 GB 机器需降到 8 个 worker 左右。**必须在 docstring 中写明。**

## 四、模块与职责划分

### 4.1 `data/parallel_fetcher.py`（拟新增）

职责**单一**：承载「必须在子进程中执行」的代码，外加负载切分与面板合并。

| 内容 | 说明 |
|---|---|
| `fetch_historical_vector_chunk` | worker 函数。**模块顶层**，取一批品种、返回 `(结果 dict, 失败清单)` |
| `split_by_trading_days` | 按交易日数把品种分成 n 份 |
| `default_max_workers` / `resolve_max_workers` | 并行度推导与上限收敛 |
| `merge_historical_vector_frames` | 合并为 `MultiIndex[calendar_time, product]` 长表面板 |
| `run_historical_vector_panel` | 对外入口（供 `DataFacade` 调用） |
| 模块 docstring | 写明全部 spawn 约束，见第十章 |

**为什么 worker 不能放进 `data/facade.py`**：`fetch_historical_vector_chunk` 必须是模块顶层函数才能被 pickle。若它与 `DataFacade` 同处一个模块，任何 import `data.facade` 的模块在 Windows `spawn` 下都会把它当作主模块重新走一遍导入，徒增耦合与踩坑概率。单独成文件后，只有真正调用多进程接口的入口才牵连它。

无循环依赖：`parallel_fetcher` 在模块顶层不 import `data.facade`（只在 worker 函数体内 import），因此 `facade.py` 可以在模块顶层放心 import `parallel_fetcher`。

### 4.2 `data/facade.py`（新增方法，不改既有方法）

新增方法只做三件事：

1. 从 `self._rollover_config` / `self._adj_config` / `self._sample_config` / `self._env_config` 取出四个 config；
2. 校验入参（`products` 非空）；
3. 品种数不足时走串行回退，否则把活交给 `parallel_fetcher`。

它**不**直接引用 `concurrent.futures`，让调度细节独立演进。

### 4.3 调用链

```
调用方
  └─ DataFacade.get_historical_vector_multiple_products_parallel(products, ...)
       │
       ├─ len(products) < MIN_PRODUCTS_FOR_PARALLEL(24) ?
       │     └─ 是 → 串行循环 self.get_historical_vector → merge_historical_vector_frames
       │
       └─ 否 → data.parallel_fetcher.run_historical_vector_panel(products, configs, ...)
                ├─ resolve_max_workers
                ├─ split_by_trading_days(products, n, master_table_dir, signature)
                ├─ 组装 tasks: [(chunk, freq, view, start, end, configs), ...]
                ├─ ProcessPoolExecutor(n)  ── with 退出即 shutdown ← 一次性
                │    └─(每个子进程) fetch_historical_vector_chunk(task)
                │         └─ DataFacade(*configs) → 逐品种 get_historical_vector
                └─ 汇总失败 → 抛 RuntimeError；否则 merge → 长表面板
```

## 五、参考实现：`data/parallel_fetcher.py`

### 5.1 模块 docstring 与常量

```python
"""
多进程数据获取：跨进程并行执行 DataFacade 的取数逻辑。

本模块只承载「必须在子进程中执行」的代码，外加负载切分与面板合并。
对外入口是 run_historical_vector_panel()，由 DataFacade 调用，不直接面向用户。

Notes
-----
本模块使用 ProcessPoolExecutor，在 Windows 上以 spawn 方式启动子进程。
spawn 不是复制父进程内存，而是重新拉起解释器并重新 import 一次调用方的主
模块，因此带来三条硬约束：

1. worker 函数必须定义在模块顶层。ProcessPoolExecutor 通过 pickle 传递
   「模块名 + 函数名」，lambda 与嵌套/局部函数都会失败，抛
   ``AttributeError: Can't pickle local object ...``。
2. 调用方必须把入口调用放进 ``if __name__ == '__main__':`` 保护内。否则每个
   子进程都会再次执行调用方脚本，递归创建进程，最终抛 ``RuntimeError: An
   attempt has been made to start a new process before the current process has
   finished its bootstrapping phase``，或 ``BrokenProcessPool``。
3. 调用方脚本的模块顶层必须保持轻量。不要在顶层构造 DataFacade 或读数据
   文件，否则每个子进程启动时都会重复一遍。

另需注意：子进程不共享父进程内存。DataFacade 内部的 feed 缓存、factory 里以
``lru_cache(maxsize=1)`` 缓存的规则组件，都是每个进程各有一份，所以子进程必须
自行重建 DataFacade——但要用调用方传下来的配置，见 fetch_historical_vector_chunk。
"""
from __future__ import annotations

import contextlib
import io
import os
from concurrent.futures import ProcessPoolExecutor
from typing import TYPE_CHECKING, Literal

if TYPE_CHECKING:
    from collections.abc import Mapping, Sequence
    from datetime import date

    import pandas as pd

    from data.config import (
        AdjustmentConfig,
        EnvironmentConfig,
        RolloverConfig,
        SamplingConfig,
    )

    # 四个配置对象，与 DataFacade.__init__ 的位置参数一一对应
    ConfigBundle = tuple[
        RolloverConfig, AdjustmentConfig, SamplingConfig, EnvironmentConfig
    ]
    # 发往子进程的任务元组
    ChunkTask = tuple[
        list[str], str, str, date | None, date | None, ConfigBundle
    ]
    # 子进程回传的结果：(成功品种, 失败品种 [(品种, 异常描述)])
    ChunkResult = tuple[dict[str, 'pd.DataFrame'], list[tuple[str, str]]]


# ContinuousContractManager 构造时会 print 换月总表文件路径，全市场 94 个品种
# 会把子进程的日志刷爆；在 worker 内部把这些 print 吞掉。
_SILENT_STDOUT = io.StringIO()

# 品种数少于此值时不做多进程：spawn 全部 worker 的固定成本约 2s，而串行每品种
# 仅约 0.14s，交叉点实测在 24 个品种附近。详见 3.5 的交叉点表。
MIN_PRODUCTS_FOR_PARALLEL = 24

# Windows 下 ProcessPoolExecutor 的进程数硬上限，超过会在构造时抛 ValueError。
WINDOWS_MAX_WORKERS = 61
```

### 5.2 worker 函数（方案的核心）

```python
def fetch_historical_vector_chunk(task: 'ChunkTask') -> 'ChunkResult':
    """
    在子进程中，为一批品种取复权主连历史价格。

    必须是模块顶层函数。ProcessPoolExecutor 靠 pickle 传递「模块名 + 函数名」，
    局部函数、嵌套函数与 lambda 都会失败。

    Parameters
    ----------
    task : ChunkTask
        ``(products, freq, view, start_date, end_date, configs)``。

    Returns
    -------
    ChunkResult
        ``(成功品种的 {品种: DataFrame}, 失败品种的 [(品种, 异常描述)])``。
        单个品种的异常在此被捕获并回传，而不是就地抛出；父进程在
        ``run_historical_vector_panel`` 汇总后统一按 fail-fast 处理，
        这样一次就能报出全部失败品种而不是只报第一个。

    Notes
    -----
    ``configs`` 必须是调用方那个 DataFacade 实例持有的四个配置对象，
    绝不能在此无参构造默认配置。``RolloverConfig.signature`` 决定换月总表文件名
    （如 ``CU_b3_r80_t1.parquet``）：若调用方用了非默认的
    ``RolloverConfig(ratio_threshold=0.8)``，而此处硬编码默认的 ``b3_r110_t1``，
    子进程会读到另一个换月总表，给出不同口径的主力判定——该错误静默发生，
    不抛任何异常。

    这里每个 chunk 都新建一次 DataFacade 不会造成额外开销：配置对象一致时，
    ``factory._create_trading_rule_components`` 的 ``lru_cache`` 会命中，
    实测重复构造耗时在毫秒级。
    """
    from data.facade import DataFacade

    products, freq, view, start_date, end_date, configs = task
    roll_config, adj_config, sample_config, env_config = configs

    facade = DataFacade(roll_config, adj_config, sample_config, env_config)

    frames: dict = {}
    failures: list = []
    with contextlib.redirect_stdout(_SILENT_STDOUT):
        for product in products:
            try:
                frames[product] = facade.get_historical_vector(
                    product=product,
                    start_date=start_date,
                    end_date=end_date,
                    freq=freq,
                    view=view,
                )
            except Exception as exc:  # noqa: BLE001 - 逐品种隔离后统一上报
                failures.append((product, f'{type(exc).__name__}: {exc}'))
    return frames, failures
```

### 5.3 负载切分

```python
def split_by_trading_days(
    products: 'Sequence[str]',
    n_chunks: int,
    master_table_dir: str,
    signature: str,
) -> list:
    """
    把品种分成 n_chunks 份，让每份的交易日总数尽量相等。

    为什么不按品种个数平均：单品种耗时差距达 54 倍（``CU`` / ``AL`` 各 7,592 个
    交易日，而 ``PT`` / ``PD`` 各 139 个）。多进程总耗时由最慢的 worker 决定，
    长尾是决定性因素。

    做法：先读出每个品种的交易日数，按降序遍历，每次把当前品种放进「已累计
    天数最少」的桶。这是最长处理时间优先（LPT）贪心，实测能把各桶的离散度压到
    1% 以内。

    Parameters
    ----------
    products : Sequence[str]
        品种代码列表。
    n_chunks : int
        目标份数，一般等于 max_workers。
    master_table_dir : str
        换月总表目录，取自 ``EnvironmentConfig.master_table_dir``，不在此硬编码。
    signature : str
        换月参数指纹，取自 ``RolloverConfig.signature``。

    Returns
    -------
    list[list[str]]
        每份的品种列表，已剔除空份。

    Notes
    -----
    代价是读一遍全部换月总表（每文件只读一列），全市场 94 个品种约 0.13-0.18s。
    换月总表缺失时按名义成本占位而不抛错，好让真正的报错仍由 worker 端以与
    串行版一致的形式抛出。
    """
    import pandas as pd

    costs: dict = {}
    for product in products:
        master_path = os.path.join(
            master_table_dir, f'{product}_{signature}.parquet'
        )
        try:
            costs[product] = len(
                pd.read_parquet(master_path, columns=['Dominant_Contract'])
            )
        except FileNotFoundError:
            # 换月总表缺失属于数据问题，交由 worker 端报错，错误信息与串行版一致。
            costs[product] = 0

    buckets: list = [[] for _ in range(n_chunks)]
    loads = [0] * n_chunks
    for product in sorted(products, key=lambda p: -costs[p]):
        i = loads.index(min(loads))
        buckets[i].append(product)
        loads[i] += costs[product]
    return [bucket for bucket in buckets if bucket]
```

### 5.4 面板合并

```python
def merge_historical_vector_frames(
    frames_by_product: 'Mapping[str, pd.DataFrame]',
    products: 'Sequence[str]',
) -> 'pd.DataFrame':
    """
    把 ``{品种: DataFrame}`` 合并成 MultiIndex 长表面板。

    与 ``DataFacade.get_historical_vector_multiple_products`` 的后处理完全一致：
    单品种结果各 copy 一份并写入 ``product`` 列，按 ``products`` 顺序逐行拼接
    （不依赖 dict 的插入顺序，以保证确定性），随后把 ``product`` 追加为第二层
    索引，最后按索引排序。
    """
    import pandas as pd

    frames = []
    for product in products:
        df = frames_by_product.get(product)
        if df is None:
            continue
        df = df.copy()
        df['product'] = product
        frames.append(df)
    if not frames:
        raise ValueError('没有任何品种成功返回数据。')

    panel = pd.concat(frames, axis=0)
    panel.set_index('product', append=True, inplace=True)
    panel.sort_index(inplace=True)
    return panel


def _format_failures(failures: 'Sequence[tuple[str, str]]') -> str:
    """把 worker 回传的失败清单拼成可读的多行异常消息。"""
    detail = '\n'.join(f'  - {product}: {message}'
                       for product, message in failures)
    return (
        f'多进程获取历史向量失败，共 {len(failures)} 个品种：\n{detail}'
    )
```

### 5.5 并行度解析

```python
def default_max_workers(n_products: int) -> int:
    """
    默认并行度：取逻辑核数的一半。

    本负载受内存带宽限制，超线程兄弟核不增加吞吐，因此有效并行度对应**物理核数**
    而非逻辑核数。实测（16 物理核 / 22 逻辑核，全 94 品种日频，4 轮中位）：

    ==========  =========  ==========
    worker 数   中位耗时    相对串行
    ==========  =========  ==========
    4           6.59s      1.82x
    6           5.67s      2.12x
    8           5.32s      2.25x
    10          5.33s      2.25x
    12          5.19s      2.31x
    16          5.38s      2.23x
    22          6.33s      1.89x
    ==========  =========  ==========

    8~16 是平坦的高效平台；直接用 ``os.cpu_count()``（本机 22）会落在平台之外，
    损失约 18%。在无新依赖的前提下无法探测物理核数，故按 2:1 超线程比例取逻辑
    核数的一半作为保守默认——本机得 11，落在平台正中。

    该比例是在单台机器上标定的启发式，不是通用结论。需要更精细的并行度时，
    由调用方显式传入 ``max_workers``。
    """
    logical = os.cpu_count() or 1
    return max(1, min(n_products, max(1, logical // 2)))


def resolve_max_workers(
    n_products: int,
    max_workers: int | None,
) -> int:
    """
    解析实际使用的子进程数。

    ``None`` 时走 ``default_max_workers``。显式传入时仍会收敛到 ``n_products``
    与 ``WINDOWS_MAX_WORKERS`` 以内：超过品种数的那部分 worker 不会被分配到
    任务，纯属白付 spawn 成本；超过 61 则会让 ProcessPoolExecutor 在构造时直接
    抛 ``ValueError``。
    """
    if max_workers is None:
        return default_max_workers(n_products)
    if max_workers < 1:
        raise ValueError(f'max_workers 必须为正整数，收到 {max_workers}。')
    return min(max_workers, WINDOWS_MAX_WORKERS, n_products)
```

### 5.6 对外入口

```python
def run_historical_vector_panel(
    products: 'Sequence[str]',
    roll_config: 'RolloverConfig',
    adj_config: 'AdjustmentConfig',
    sample_config: 'SamplingConfig',
    env_config: 'EnvironmentConfig',
    start_date: 'date | None' = None,
    end_date: 'date | None' = None,
    freq: str = '1d',
    view: Literal['scheduled', 'realized'] = 'scheduled',
    max_workers: int | None = None,
) -> 'pd.DataFrame':
    """
    多进程并行获取多品种复权主连历史价格，合并为长表面板。

    这是本模块的对外入口，由 ``DataFacade`` 调用。调用方须自行确认品种数量
    值得并行（见 ``MIN_PRODUCTS_FOR_PARALLEL``）。

    Parameters
    ----------
    products : Sequence[str]
        品种代码列表，非空。
    roll_config, adj_config, sample_config, env_config
        四个配置对象，透传给每个子进程重建 ``DataFacade``。**必须**来自调用方
        的 facade 实例，不得用默认值替代，理由见
        ``fetch_historical_vector_chunk`` 的 Notes。
    start_date, end_date : date | None, optional
        闭区间交易日边界，``None`` 为各品种最早 / 最晚可用日期。
    freq : str, default '1d'
        K 线频率，同 Pandas Offset aliases。
    view : {'scheduled', 'realized'}, default 'scheduled'
        计划或实际视图。
    max_workers : int | None, optional
        最大子进程数。``None`` 时按 ``resolve_max_workers`` 推导。

    Returns
    -------
    pd.DataFrame
        MultiIndex[calendar_time, product] 的长表面板，与串行版
        ``get_historical_vector_multiple_products`` 的输出逐值一致。

    Raises
    ------
    ValueError
        ``products`` 为空，或 ``max_workers`` 非正整数，或没有任何品种返回数据。
    RuntimeError
        任一品种取数失败。失败清单在异常消息中逐行列出；此为 fail-fast 语义，
        调用整体失败而不返回缺品种的部分结果。
    """
    if not products:
        raise ValueError('products 列表不能为空。')

    n_workers = resolve_max_workers(len(products), max_workers)

    tasks = [
        (chunk, freq, view, start_date, end_date,
         (roll_config, adj_config, sample_config, env_config))
        for chunk in split_by_trading_days(
            products, n_workers,
            master_table_dir=env_config.master_table_dir,
            signature=roll_config.signature,
        )
    ]

    frames: dict = {}
    failures: list = []
    # with 语句退出时自动 shutdown(wait=True)，这就是「一次性调用」的全部含义。
    with ProcessPoolExecutor(max_workers=n_workers) as executor:
        for chunk_frames, chunk_failures in executor.map(
            fetch_historical_vector_chunk, tasks
        ):
            frames.update(chunk_frames)
            failures.extend(chunk_failures)

    if failures:
        raise RuntimeError(_format_failures(failures))

    return merge_historical_vector_frames(frames, products)
```

            最大子进程数。默认 None 时取逻辑核数的一半——该负载受内存带宽限制，
            超线程兄弟核不增加吞吐，取逻辑核数的一半实测落在高效平台内，比直接用

        Returns
        -------
        pd.DataFrame
            MultiIndex[calendar_time, product] 的长表面板，列与
            ``get_historical_vector_multiple_products`` 一致。

        Raises
        ------
        ValueError
            ``products`` 为空，或 ``max_workers`` 非正整数。

            adj_config=self._adj_config,
            sample_config=self._sample_config,
            env_config=self._env_config,

            end_date=end_date,

## 八、任务切分设计

### 8.1 结论：每 chunk 一任务 + 静态 LPT

### 8.2 实测依据（w=16，全 94 品种）

| 粒度 | 任务数 | 总耗时 | 面板一致 |
|---|---|---|---|
| 每块一任务（静态 LPT，16 块） | 16 | **4.67s** | 是 |
| 每品种一任务（进程池动态派活） | 94 | 5.60s | 是 |

**与预期相反**：原本认为「一品种一任务」能让 `ProcessPoolExecutor` 动态派活、自动均衡，无需静态切分。实测反而慢 0.93s。

原因是任务过碎：94 个任务意味着 78 次额外交接，每次要经历「worker 干完 → pickle → 走管道 → 父进程读取」，交接期间 worker 空转。总开销约 10ms × 78 ≈ 0.8s，与实测差值吻合。

### 8.3 LPT 均衡效果

按「每个 worker 分到的交易日数」衡量（数值为「最重 chunk / 理想值」）：

| workers | 连续切片 | 轮转分配 | 按交易日 LPT |
|---|---|---|---|
| 2 | 1.08x | 1.01x | **1.00x** |
| 4 | 1.09x | 1.02x | **1.00x** |
| 8 | 1.13x | 1.23x | **1.00x** |
| 16 | 1.18x | 1.41x | **1.01x** |

### 8.4 诚实的补充：当前规模下 LPT 收益在噪声里

w=8 实测三种策略：连续切片 4.54s / 轮转分配 4.55s / LPT 4.76s，全在测量噪声范围内。原因是总计算量只有 13s，而固定启动成本吃掉约 2.5s；LPT 带来的 13% 改善只作用在那 2s 多的计算段上，约 0.2s。

因此这 20 行切分代码**在当前日频全市场规模下基本是保险而非刚需**。它的价值在于为分钟级 `freq` 预留——那时工作时长几十倍，长尾才会真正决定总时间。如实记录此点，避免后续误以为「删掉切分也不会变慢」。

### 8.5 切分粒度约束

**一个品种必须完整落在同一个 worker 内部。**

这条是硬约束，理由与串行版完全不同：每个品种的 `ResearchFeed` 与 `_research_master_table`
是一次性构建的昂贵对象。若把单个品种拆给多个 worker，每个 worker 都要重建一次，
单份工作的膨胀（见 3.2）会被成倍放大。按品种切分天然规避该问题，因此
`parallel_fetcher` **不提供**把单品种再切开的接口。

### 8.6 串行/并行的交叉点：`MIN_PRODUCTS_FOR_PARALLEL`

spawn 全部 worker 的固定成本约 2s，而串行每品种仅约 0.14s，因此品种数少时多进程是净亏损。实测（固定种子随机抽样，最优 worker 数）：

| 品种数 | 串行 | 多进程 | 比值 |
|---|---|---|---|
| 1 | 0.26s | 1.56s | **0.16x** |
| 2 | 0.38s | 1.68s | 0.23x |
| 4 | 0.76s | 1.82s | 0.42x |
| 8 | 1.03s | 2.44s | 0.42x |
| 12 | 1.71s | 2.87s | 0.60x |
| 16 | 2.44s | 3.36s | 0.72x |
| **24** | 3.92s | 4.03s | **0.97x（交叉点）** |
| 32 | 5.45s | 4.13s | 1.32x |
| 48 | 8.06s | 5.70s | 1.41x |
| 94 | 13.03s | 4.87s | 2.63x |

交叉点在 24 个品种附近，故 `MIN_PRODUCTS_FOR_PARALLEL = 24`。

**该阈值依赖单品种成本**：日频下每品种约 0.14s。若换成分钟级 `freq`，单品种成本
上升几十倍，交叉点会大幅左移，届时应调低此常量。docstring 中已提示调用方在
品种数少时直接用 `get_historical_vector`。

## 九、异常语义

### 9.1 选定方案：fail fast（方案 A）

任一品种异常 → 整个调用抛出。选择理由：与串行版现有契约一致，且**不引入新的静默失败模式**。若采用「跳过并汇总」，返回的面板会少品种但调用方可能无感知——对量化研究而言，静默缺品种比明确报错危险得多。

需要说明的是，「fail fast」指**调用整体失败、不返回缺品种的部分结果**，而非提前中断其余 worker。实现上是等所有 chunk 跑完后统一检查失败清单，这样一次能报出全部失败品种：

```
RuntimeError: 多进程获取历史向量失败，共 1 个品种：
  - NOT_EXIST_XYZ: FileNotFoundError: 未找到 NOT_EXIST_XYZ 的品种规则配置文件: db\rules\product_meta\NOT_EXIST_XYZ.yaml
```

（上述为实测输出，错误信息由底层组件原样带出，与串行版一致。）

### 9.2 chunk 粒度带来的定位问题及解法

一个 chunk 含约 6 个品种，异常发生在 chunk 内部。若直接让 `executor.map` 抛出，只能定位到 chunk，**无法定位到品种**——这比串行版（一次只跑一个品种，出错即指名）差。

解法：**worker 内部做 per-product 捕获**，失败项随结果一起回传（见 5.2 的 `failures` 列表），父进程汇总后统一抛出。这样同时拿到 chunk 级任务带来的低交接开销（8.2）与 per-product 级的错误定位能力。

### 9.3 异常包装层次

worker 侧的异常经进程池回传时会被 `multiprocessing` 包装成 `_RemoteTraceback`，原始堆栈信息**得以保留**。本方案的做法是在 worker 内就转成字符串 `(品种, '异常类型: 消息')` 回传，父进程再组织为业务语义异常。代价是丢失了 worker 侧的完整堆栈；收益是错误定位精确到品种且消息可读。若需要完整堆栈，可改为把异常对象本身回传（自定义异常类默认可 pickle）。

### 9.4 建议的异常类型

复用串行版的 `RuntimeError`（消息含品种名），使调用方若同时使用两种接口时异常处理逻辑不必分叉。此项在实现阶段最终确认。

## 十、配置传递设计

### 10.1 核心规则

子进程重建 `DataFacade` 时，四个 config **必须**来自调用方那个 facade 实例的
`_rollover_config` / `_adj_config` / `_sample_config` / `_env_config`，随任务元组一起 pickle 传递。

### 10.2 这是正确性问题，不是风格问题

`RolloverConfig.signature` 决定换月总表文件名（`{品种}_{signature}.parquet`）。若子进程硬编码默认配置：

| 调用方实际传入 | 子进程硬编码默认 | 后果 |
|---|---|---|
| `RolloverConfig(ratio_threshold=0.8)` → signature `b3_r80_t1` | `RolloverConfig()` → `b3_r110_t1` | 子进程读到**另一个换月总表**，得到与父进程口径不同的主力判定 |

**该错误静默发生、不抛异常、结果看似合理。** 因此：

- worker 内部**不允许**出现任何四类 config 的无参构造；
- 代码评审以「worker 函数体内零个 config 构造」为硬性检查项。

### 10.3 可 pickle 性

四个 config 均为模块级 `@dataclass(frozen=True)`，可 pickle：

| config | pickle 字节数 | 反序列化后相等 | hash 一致 |
|---|---|---|---|
| `RolloverConfig` | 116 B | 是 | 是 |
| `AdjustmentConfig` | 98 B | 是 | 是 |
| `SamplingConfig` | 127 B | 是 | 是 |
| `EnvironmentConfig` | 718 B | 是 | 是 |

`EnvironmentConfig` 全部字段为 `str` / `int`，无不可序列化成员。hash 一致这一点有额外意义：`factory._create_trading_rule_components` 是 `lru_cache(maxsize=1)` 且以 `env_config` 为键，同一进程内重复构造 facade 会命中缓存，故 5.2 中每个 chunk 都新建 `DataFacade` 无额外成本。

### 10.4 子进程不共享内存

Windows `spawn` 出来的子进程是**全新解释器**，以下父进程状态子进程一概看不到：`DataFacade._research_feeds` 等 feed 缓存、`factory` 的 `lru_cache`、已读入内存的 parquet / master_table。

因此「把父进程的 facade 传过去」既不可行也无意义。正确做法只有一条：**传 config，在子进程重建**。

## 十一、调用方约束与已知坑

本节内容需**同时**写入 `data/parallel_fetcher.py` 模块 docstring（见 5.1）与新方法的 docstring（见第六章）。

### 11.1 必须有 `if __name__ == '__main__':` 保护

| 平台 | 子进程启动方式 | 缺失保护的后果 |
|---|---|---|
| Linux | `fork`，复制父进程内存 | 基本无影响 |
| **Windows** | **`spawn`，全新解释器 + 重新 import 主模块** | 无限递归创建进程 → `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase` / `BrokenProcessPool` |

### 11.2 顶层代码必须保持轻量

调用方脚本若在**模块顶层**就构造 `DataFacade` / 读 parquet，则每个子进程启动时都会执行一遍（`spawn` 会重新 import 主模块）。16 个 worker × 冗余初始化是纯粹的浪费。所有准备工作应放进 `main()` 内。

### 11.3 worker 函数必须是模块顶层函数

`spawn` 通过 pickle 传递「模块名 + 函数名」。以下写法**会失败**（均为实测错误信息）：

- `lambda`：`AttributeError: Can't pickle <lambda>`
- 闭包 / 嵌套函数：`AttributeError: Can't get local object 'make_worker.<locals>._worker'`

### 11.4 相对路径可用：cwd 与 sys.path 均被继承

`EnvironmentConfig` 中数据路径均为相对路径（`./db/rules/...`）。实测确认 `spawn` 子进程**继承父进程的 cwd 与 sys.path**，`import data` 无需设置 `PYTHONPATH`：

```
PYTHONPATH = None
子进程 cwd = D:\量化策略\CTA策略\Multi-factor Trend Following
import data 成功? True
子进程 pid = [22252, 13668]   ← 确为独立进程
```

### 11.5 Windows 进程数硬上限 61

`ProcessPoolExecutor` 在 Windows 上要求 `max_workers <= 61`，否则构造时直接抛
`ValueError: max_workers must be <= 61`。这是实测踩到的（传 94 时报错）。`resolve_max_workers` 已做收敛。

### 11.6 内存放大 3.5x

见 3.4。必须在 docstring 中写明，并建议低配机器下调 `max_workers`。

### 11.7 `max_workers` 不应超过物理核数

见 3.2。默认 `None` 走「逻辑核数的一半」的保守启发式，更精细的控制由调用方自行决定。

| 议题 | 说明 |

| 常驻进程池 | 稳态可达 5.78x（w=16），是本方案上限 2.7x 的两倍。适合「多日期区间 / 多轮因子反复取数」的研究流程。届时需设计池的生命周期管理（何时创建、何时回收、是否复用已缓存的 `ResearchFeed`） |

### 13.2 最重要的一条：配置传递不能只是「跑通」

### 13.3 必须实证而不能推理的风险：pytest + spawn

pytest 的入口在 `__main__` 中，而 `spawn` 会重跑 `__main__`。原型阶段探测到本进程
`__main__.__spec__ = None`，意味着会走「按路径重跑入口文件」分支——**存在让 pytest 自身
被重复执行的风险**。

**处理方式**：实现后专门写一个走进程池的 pytest 用例来实证，不靠阅读 `multiprocessing` 源码下结论。

### 13.4 建议的 pytest 用例结构

- **纯函数级（不经进程池，快）**：`resolve_max_workers` 边界、`split_by_trading_days`

- **边界**：`products=[]`、`max_workers=1`、`max_workers > len(products)`、

## 十五、已知边界

1. **一次性调用的上限约 2.7x**，受 Windows spawn 启动成本（约 2.5s @w=16）限制。想要更高需常驻进程池（稳态 5.78x），属第十二章议题。
2. **超过物理核数无收益**，22 worker 实测 1.89x，低于 12 worker 的 2.31x。
3. **默认并行度是启发式**。`os.cpu_count() // 2` 是在单台机器（16 物理核 / 22 逻辑核）上标定的，无新依赖时无法探测真实物理核数。换机器时应重新标定。
4. **内存放大 3.5x**（908 MB → 3,189 MB @w=16），低配机器需下调 `max_workers`。
5. **`MIN_PRODUCTS_FOR_PARALLEL = 24` 依赖单品种成本**。日频下每品种约 0.14s；换成分钟级 `freq` 后交叉点会大幅左移，该常量需重新标定。
6. **LPT 切分在当前日频规模下收益在噪声内**，其价值在于为分钟级 freq 预留（8.4）。
7. **逐笔流接口不适用本方案**（生成器不可 pickle），逐笔类接口的多进程化需另行设计。
8. **worker 侧完整堆栈丢失**。为换取精确到品种的错误定位，worker 内把异常转成字符串回传（9.3）。
9. **线程版已改为串行**。初稿曾决定保留线程版以服务「不 fork 子进程」的环境；实测该负载下线程比串行慢 6%–27%（§1.2），中间态无价值，故直接改为串行。这些环境（受限 notebook、部分 CI 沙箱）改用串行版同样可跑，且省去 spawn 限制。
10. **本方案的多进程语义仅在 Windows `spawn` 下完成验证**。Linux `fork` 下父子共享内存、`lru_cache` 状态与 spawn 不同，行为差异（尤其异常传播与 fd 继承）未做验证。
