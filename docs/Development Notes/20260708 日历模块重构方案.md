# 日历模块重构方案

## 背景

当前 `data.calendar.calendar` 与 `data.rules.trading_rule_service` 存在类型检查层面的循环导入告警：

```text
data.calendar.calendar
  -> TYPE_CHECKING: data.rules.trading_rule_service.TradingRuleService
  -> TYPE_CHECKING: data.calendar.calendar.ExchangeTradingCalendar
```

这不是运行时真实循环导入，因为相关引用位于 `if TYPE_CHECKING:` 中；但 BasedPyright 会分析类型导入图，因此仍会提示 `cycle detected in import chain`。

此外，当前 `ExchangeTradingCalendar` 在构造时绑定单一 `exchange`，而 `TradingRuleService` 是面向所有合约/品种的统一门面。若向其中注入一个绑定单一交易所的日历实例，会让 `TradingRuleService` 在概念上变得有状态，不够自然。

## 目标

1. 消除 BasedPyright 的循环导入告警。
2. 明确区分交易所级日历与品种级日历。
3. 让 `TradingRuleService` 继续保持统一、无品种/交易所绑定的服务形态。
4. 保留交易所日历数据的懒加载与缓存能力，避免重复读取 CSV。

## 方案

### 1. 拆分交易所级日历模块

新增模块：

```text
data/calendar/exchange_calendar.py
```

将原 `ExchangeTradingCalendar` 从 `data/calendar/calendar.py` 移入该模块，并改名为：

```python
ExchangeCalendar
```

职责边界：

- `ExchangeCalendar`：只负责交易所交易日序列，例如判断交易日、查找下一个交易日、根据日历时间戳推断交易日。
- `ProductCalendar`：负责品种/合约级交易时间逻辑，例如 session id、minute offset、标准时间戳生成等。

### 2. 将 `ExchangeCalendar` 改为不绑定单一交易所

当前接口类似：

```python
calendar = ExchangeTradingCalendar(exchange='SHFE', calendar_dir=calendar_dir)
calendar.is_trading_date(trading_date)
```

建议改为：

```python
calendar = ExchangeCalendar(calendar_dir=calendar_dir)
calendar.is_trading_date(exchange, trading_date)
calendar.next_trading_date(exchange, trading_date)
calendar.get_trading_date(exchange, calendar_timestamp)
```

也就是说，`exchange` 从构造参数移动到方法参数。

注意：这里的 `ExchangeCalendar` 并非完全无内部状态。它仍然可以持有：

```python
self.calendar_dir
self._exchange_dates_cache
```

这类状态属于数据源配置和性能缓存，不代表对象绑定某个业务实体，因此不会破坏统一服务的语义。

### 3. 将 `TradingCalendar` 重命名为 `ProductCalendar`

当前 `TradingCalendar` 实际上是绑定某个 `product` 的品种级日历服务，因此建议重命名为：

```python
ProductCalendar
```

推荐模块结构：

```text
data/calendar/exchange_calendar.py
    ExchangeCalendar

data/calendar/product_calendar.py
    ProductCalendar
```

如果希望降低一次性改动风险，可以短期保留兼容别名：

```python
TradingCalendar = ProductCalendar
```

### 4. 调整 `TradingRuleService` 对日历的依赖

`TradingRuleService` 不应注入绑定单一交易所的日历实例，而应注入统一的 `ExchangeCalendar`：

```python
class TradingRuleService:
    def __init__(
        self,
        meta_manager,
        registry_manager,
        holiday_manager,
        exchange_calendar: ExchangeCalendar,
        daily_status_manager=None,
    ):
        ...
```

在 `get_trading_sessions(contract, trading_date, view)` 内部，通过已有依赖推导交易所：

```python
product = self.registry_manager.get_instrument_registry(contract).product
exchange = self.meta_manager.get_static_meta(product).exchange

if not self.exchange_calendar.is_trading_date(exchange, trading_date):
    ...
```

这样调用方仍只需要传入 `contract` 和 `trading_date`，不需要关心交易所。

### 5. 可选：使用 Protocol 降低类型耦合

如果希望进一步降低 `TradingRuleService` 对具体实现类的依赖，可以定义窄接口：

```python
from datetime import date
from typing import Protocol

class ExchangeCalendarLike(Protocol):
    def is_trading_date(self, exchange: str, trading_date: date) -> bool:
        ...
```

然后 `TradingRuleService` 依赖 `ExchangeCalendarLike`，而不是具体的 `ExchangeCalendar`。

这样做的意义是：`TradingRuleService` 只关心注入对象“能判断某交易所某日期是否为交易日”，不关心它具体是哪一个类。测试时也可以传入轻量 fake calendar。

## 预期收益

- 消除 `data.calendar.calendar` 与 `data.rules.trading_rule_service` 之间的类型导入环。
- `ExchangeCalendar` 与 `ProductCalendar` 职责更清晰。
- `TradingRuleService` 不再被单一交易所状态污染，更符合统一门面服务定位。
- 后续测试更容易构造替身对象，尤其适合用 `Protocol` 做窄接口依赖。

## 建议执行顺序

1. 新建 `data/calendar/exchange_calendar.py`，迁移并重命名 `ExchangeTradingCalendar` 为 `ExchangeCalendar`。
2. 调整 `ExchangeCalendar` 接口，将 `exchange` 从构造参数改为方法参数，并增加内部按交易所缓存。
3. 将 `TradingCalendar` 重命名为 `ProductCalendar`，必要时保留 `TradingCalendar = ProductCalendar` 兼容别名。
4. 调整 `TradingRuleService`，注入统一的 `ExchangeCalendar`，并在内部根据 `contract -> product -> exchange` 推导交易所。
5. 更新 `factory`、feed、storage、tests 中相关引用。
6. 运行静态检查和核心日历/交易规则测试，确认循环导入告警消失。
