# V1 Bar级最小闭环系统开发-代码写作方案

## 1. 开发目标

V1 的目标不是实现完整期货回测平台，而是建立第一条可运行的 Bar 级交易状态闭环：

```text
DataFacade -> BarMarketFeed -> Strategy -> TargetPosition -> Order -> Fill -> Account -> Performance
```

本阶段必须守住以下不变量：

- 策略收益不得由 `Signal * Return` 直接计算。
- 策略使用复权连续价格 `Adj_Close`。
- 成交使用物理合约真实价格 `Raw_Open`。
- 实际持仓只能由 `Fill` 改变。
- 账户是现金、持仓、PnL 和权益的唯一权威来源。
- 当前 Bar 收盘产生的信号，只能在下一根 Bar 开盘成交。

## 2. 模块划分

沿用仓库已有目录，避免同时出现重复语义目录：

- `backtester/`：`BarMarketEvent`、`BarMarketFeed`、`BacktestConfig`、`BacktestEngine`。
- `strategy/`：策略接口、`StrategyContext`、`TimeSeriesMomentumStrategy`。
- `portfolio/`：`TargetPosition`、`Order`、`OrderManager`。
- `executor/`：下一 Bar 开盘成交模型、固定滑点、简化手续费。
- `account/`：`Fill`、`Position`、`Account`、`AccountSnapshot`。
- `analytics/`：`PerformanceRecorder`、权益曲线、日志和基础绩效指标。

V1 暂不创建 `events/`。事件对象放在各自领域模块中，等事件类型明显增多后再抽象统一事件层。

## 3. 编码顺序

### Step 1：核心数据模型

先定义轻量对象，不写复杂业务：

- `BarMarketEvent`
- `TargetPosition`
- `Order`
- `Fill`
- `Position`
- `AccountSnapshot`
- `BacktestConfig`
- `MomentumConfig`

`BarMarketEvent` 从 `ResearchFeed` 输出转换而来，至少包含 product、contract、timestamp、trading_date、复权 OHLC、原始 OHLC 和 is_roll。

### Step 2：BarMarketFeed

在 `DataFacade` 和 `BacktestEngine` 中间增加薄适配层：

- 调用 `DataFacade.get_historical_vector(...)`。
- 校验 `Dominant_Contract`、`Adj_*`、`Raw_*`、`trading_date`、`is_roll`。
- 将 DataFrame 行转换为 `Iterator[BarMarketEvent]`。
- 不重建日历、Bar 聚合、主力识别、复权和清洗逻辑。

### Step 3：Account

账户模块优先脱离策略单独测试：

- `apply_fill(fill)` 是唯一能改变持仓的入口。
- 支持开多、平多、开空、平空、加仓、减仓、多转空、空转多。
- `mark_to_market(bar)` 使用当前物理合约 `Raw_Close`。
- 盈亏必须乘以合约乘数。
- 合约乘数通过可注入的 `multiplier_provider` 获取，后续可接入现有 `InstrumentRegistry.multiplier`。

V1 账户恒等式：

```text
equity = initial_cash + realized_pnl + unrealized_pnl - commission
```

V1 不实现保证金占用、今昨仓、真实逐日盯市。

### Step 4：Execution / Commission / Slippage

第一版只实现市价单下一 Bar 开盘全部成交：

- BUY：`fill_price = bar.raw_open + slippage`
- SELL：`fill_price = bar.raw_open - slippage`
- 默认滑点为 0，但保留 `FixedSlippageModel`。
- 默认手续费为固定每手费用，但保留按名义金额费率模型。

### Step 5：OrderManager

`OrderManager` 负责把目标仓位翻译为交易意图：

```text
delta = target_quantity - actual_quantity
```

- `delta > 0` 生成 BUY。
- `delta < 0` 生成 SELL。
- `delta == 0` 不生成订单。
- 订单使用当前 `BarMarketEvent.contract` 作为物理交易合约。

最小换月模型：

- 如果同一品种仍持有旧主力合约，而当前主力合约已经变化，先生成旧合约平仓订单。
- 然后根据当前主力合约实际持仓与目标仓位生成新合约订单。

### Step 6：Strategy

策略接口为：

```python
Strategy.on_bar(event, context) -> TargetPosition | None
```

策略只表达目标仓位，不允许修改账户、创建 Fill、计算手续费或直接计算最终收益。

首个策略为 `TimeSeriesMomentumStrategy`：

- 默认 `lookback = 20`。
- 默认 `quantity = 1`。
- 使用 `Adj_Close` 计算动量。
- 动量为正，目标 `+quantity`。
- 动量为负，目标 `-quantity`。
- 动量为 0，目标 `0`。

### Step 7：BacktestEngine

每根 Bar 的调用顺序固定：

1. 新 Bar 到达。
2. 用当前 Bar `Raw_Open` 执行上一期 pending orders。
3. Fill 进入 Account。
4. 当前 Bar 收盘后用 `Raw_Close` mark-to-market。
5. 更新 StrategyContext 历史。
6. Strategy 使用截至当前 Bar 的信息生成 TargetPosition。
7. OrderManager 生成 Order。
8. Order 进入 pending 队列。
9. Account 生成 Snapshot。
10. PerformanceRecorder 记录状态。

引擎只做调度，不包含账户、执行、策略的业务细节。

### Step 8：PerformanceRecorder

记录器只忠实保存状态演化：

- targets
- orders
- fills
- account_snapshots
- equity_curve
- trade_log
- order_log
- position_history

基础指标包括总收益率、年化收益率、年化波动率、Sharpe、最大回撤、交易次数、总手续费和净收益。

## 4. 测试方案

V1 测试优先级高于报表功能。

- 模型测试：核心 dataclass 字段、不可变性、基础校验。
- OrderManager 测试：空仓到多、多仓保持、多转空、空转多、换月平旧开新。
- Execution 测试：BUY/SELL 下一 Bar 开盘成交，滑点方向正确，成交价使用 `Raw_Open`。
- Account 黄金路径：开多平多、开空平空、多转空、空转多。
- 时间因果测试：Bar t 的 close 触发信号，不得在 Bar t open 成交，只能在 Bar t+1 open 成交。
- 端到端黄金测试：用人工 Bar 手工计算 target/order/fill/position/equity。
- 真实数据冒烟测试：用 `DataFacade` 跑单品种日频 20 Bar 动量策略。

## 5. 当前主要盲点

- 账户语义盲点：V1 暂不做保证金、今昨仓和真实逐日盯市，策略结论只能被视为最小闭环结果。
- 换月执行盲点：最小换月模型不处理提前换月、双合约过渡、流动性冲击和分批换月。
- 成本模型盲点：手续费、滑点、冲击成本被简化，短周期和高换手策略可信度受限。
- 多品种组合盲点：V1 尚未处理组合级资金分配、风险标准化和多品种同步时间轴。
- 数据接口盲点：Bar 数据接口清晰，但合约乘数等交易规则需要通过适配层接入账户。
- 测试数据盲点：核心回归测试必须使用人工 Bar，避免被本机原始数据路径绑架。

## 6. V1 完成标准

V1 不能以“代码写完”为完成标准，而应满足：

- 能运行一个完整趋势策略。
- 每一笔 Fill 都能追溯到 Target 和 Order。
- 回测收益完全由 Fill 和 Account 产生。
- 成交价格使用真实物理合约价格。
- 当前 Bar 信息不会回到当前 Bar 开盘成交。
- 核心黄金路径测试全部通过。
